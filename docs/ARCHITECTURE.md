## 1. Goals and motivation

### 1.1 What phasor is for

1. **Parallel parameter sweeps**: thousands of parameter sets as independent columns of one run.
2. **Parallel backtests across symbols or multi-asset accounts**: a shared account is a contiguous group of columns (§8.3).
3. **Factor expressions at scale**: Qlib-style expressions (§5) over whole panels, feeding signals and simulation directly.

Secondary: strategies written in NautilusTrader's style later (source-level portability, §17.1).

### 1.2 Two findings that shaped the design

| Finding | Evidence | Consequence |
|---|---|---|
| Porting a branchy loop to Rust buys nothing | vectorbt's own Rust backend: `simulate_from_orders` **0.73×–1.15×** vs Numba, but **6–10×** on vectorizable ops (`diff`, `pct_change`, shifts at 1000×100); phasor's harness reproduces 0.74×–0.82× (§15.1) | speed must come from design, not the compiler |
| The event-driven reference cannot sweep in parallel | NautilusTrader `BacktestNode::run()` is a sequential `for`; state is `Rc<RefCell<..>>` behind a global message bus; ~1.2–1.9 µs/event | parallelism is the opening |

Result (§15.1): the loop is 2.6×–3.3× faster than vectorbt's Numba loop on one
thread, 9.7×–12.1× on 4 threads. How much each design choice (column-major scans,
stack-local state, `FlexArray` scalar fast path, threads) contributes is not measured.

### 1.3 What phasor is not

- Not event-driven yet: no order book, ticks or latency model; execution is on bars.
- Not a data vendor: library crates never download or write; network code lives in `examples/`.
- Not an allocator or risk system: sizing is what the caller asks for.

## 2. System overview

### 2.1 The pipeline

![Pipeline: local files → bar panel → factor matrices → signals → simulation → records → analysis; factors run in parallel over symbols, simulation in parallel over accounts](img/en/pipeline.svg)

Every arrow is a function call on in-memory arrays; there is no dataframe
between stages. Factors are `Matrix`, parameters are borrowed through `FlexArray`
(§3.3), records are struct-of-arrays (§9).

### 2.2 Two tiers, unified by records and one execution kernel

```mermaid
flowchart LR
  A["Tier A (phase 1)<br/>vectorized: arrays in"] --> K["phasor_exec::execute_order"]
  B["Tier B (phase 2, planned)<br/>event-driven Strategy"] -.-> K
  K --> R["RecordSink → same record schemas"]
  R --> P["phasor-analysis (written once)"]
```

Nanoseconds per column-bar versus microseconds per event: the vectorized tier
cannot be realistic and the event tier cannot be fast. They share output and
kernel instead, so a sweep can be validated against a replay column by column.
Phase 1 therefore keeps two constraints: the kernel runs for a single bar in
isolation, and records are written through the `RecordSink` trait (§9.3).

vectorbt's Rust backend refuses callback functions, so `from_order_func` stays in
Numba. `order_func_nb(OrderContext) -> Order` and Nautilus's `on_bar` have the same
shape; in Rust that is a monomorphized trait call, so a Nautilus-style API can
double as a native `from_order_func`.

### 2.3 Crates

![Crate dependency graph: phasor-core at the bottom; model, generic, signals above it; exec, data, expr, indicators; records, sim; analysis on top; phasor and phasor-py are façades](img/en/crates.svg)

| Crate | Role |
|---|---|
| `phasor-core` | `Matrix`, `FlexArray`, column labels, float tolerances, `Error` (§3), seeded random draws keyed by `(seed, row, col)`; no external deps |
| `phasor-model` | execution enums, ids, `BarType`, `OhlcvPanel`, fixed-point `Price`/`Quantity` (§3.6) |
| `phasor-generic` | rolling / expanding / EWM windows, shifts, fills, crossovers; seeded synthetic prices (`random_walk`, `gbm`, `ohlc_from_close`) |
| `phasor-signals` | signal cleaning, exit generation, ranks, ranges (§6.2) |
| `phasor-indicators` | MA, MSTD, BBANDS, RSI, STOCH, MACD, ATR, OBV with sweeps (§6.4) |
| `phasor-expr` | expression parser, graph compiler, native + Polars backends, Alpha158/360 (§5) |
| `phasor-exec` | the order execution kernel (§7) |
| `phasor-records` | record schemas, sinks, trades, drawdowns, mapped arrays (§9) |
| `phasor-sim` | `from_orders` / `from_signals` loops, stops, groups, parallel runners (§8) |
| `phasor-analysis` | `Portfolio`, value/returns chain, metrics, stats, aggregation (§10) |
| `phasor-data` | CSV / Parquet / catalog → Arrow → panels, point-in-time alignment (§4) |
| `phasor` | façade, `prelude`, `SignalSweep` (§6.1); feature `data` adds phasor-data |
| `phasor-py` | PyO3 extension `phasor._phasor` + Python package `phasor` (§12) |

External runtime dependencies: `rayon` (phasor-expr), optional `polars` 0.46
(phasor-expr), `arrow-*`/`parquet` 59 + `csv` (phasor-data), `pyo3`/`numpy` 0.29
(phasor-py). phasor-sim uses only `std::thread::scope`.

### 2.4 Scope decisions

| Decision | Detail |
|---|---|
| Accounts independent by default | every column has its own cash; `cash_sharing` + `group_lens` makes contiguous columns one account (§8.3) |
| Orders sequential within an account | a call sequence per bar; `call_seq="auto"` puts sells before buys |
| Metrics per account, records per symbol | returns come from account equity; orders/trades/logs keep their column |
| Bars only | funding, news etc. enter as factor inputs via point-in-time alignment (§4.4) |
| Rust engine, Python boundary | schemas, strings and callbacks stay outside the loops; decoders run at load time |
| Sweeps do not copy prices | OHLCV stays `[T, S]`; `FlexArray::MappedColumns` (`column_map`) maps sweep columns to it (§3.3) |

## 3. Foundations: phasor-core and phasor-model

### 3.1 The column axis

![Column axis: col = param_idx × n_symbols + symbol_idx; parameters repeat, symbols tile; each account is a contiguous slice; in memory each column is one contiguous run](img/en/columns.svg)

- Parameter labels **repeat** (`Level::repeat`), symbol labels **tile** (`Level::tile`), in `crates/phasor-core/src/columns.rs`.
- **Contiguity**: one parameter set occupies adjacent columns, so a shared account is a slice (`group_lens=[2,2,2]`). The simulator only needs shape and group lengths.
- The layout is a constructor convention (`Level`, `column_of`, `SignalSweep`, `phasor.strategy.sweep`), pinned by `one_parameter_combination_occupies_contiguous_columns`, not checked at runtime.
- **Labels**: `Columns { levels, n_cols }`; `Label = Int | Float | Str | Bool` (floats by bit pattern). `group_indices(level)` drives by-parameter aggregation (§10.5).

### 3.2 Memory layout

- `Matrix { data: Vec<f64>, n_rows, n_cols }`; `column(c)` is a zero-copy `&[f64]`.
- Column-major because the column is the unit of work: a simulation scans one column (or adjacent group), a factor is evaluated one symbol at a time (§5.4), a thread owns a range of columns.
- `OhlcvPanel` is struct-of-arrays (one buffer per field; empty = not provided).
- NumPy defaults to row-major, so every array crossing into Rust must be Fortran-ordered (§12.2).

### 3.3 Broadcasting with `FlexArray`

Materializing every parameter would cost `T × C × 8` bytes each (1.6 GB at
100k × 2,000). `FlexArray<'a, T>` borrows what it was given:

| Variant | `get(row, col)` reads |
|---|---|
| `Scalar(T)` | the value (no memory access) |
| `PerColumn(&[T])` | `values[col]` |
| `PerRow(&[T])` | `values[row]` |
| `MappedColumns { data, n_rows, columns }` | `data[columns[col] * n_rows + row]` |
| `Full { data, n_rows }` | `data[col * n_rows + row]` |

`get` is one inlined match; `varies_by_row()` lets loops hoist per-column
constants. Checked constructors return `Error::FlexLen`. `MappedColumns` is what
makes sweeps cheap: 50 parameter sets × 100 symbols address 5,000 logical price
columns while only 100 exist (`column_map` in Python).

### 3.4 The float tolerance layer

`crates/phasor-core/src/math.rs`:

| Item | Rule |
|---|---|
| `REL_TOL`, `ABS_TOL` | `1e-9`, `1e-12`, as the reference |
| `is_close(a, b)` | PEP 485, except **NaN and ±inf are never close, not even `inf` to `inf`**: infinity is a live sentinel (`size=+inf` = all you can, `price=+inf` = close) |
| `is_close_or_less`, `is_less` | used for every affordability decision, never raw `<=` (§7.5) |
| `add(a, b)` | returns exactly `0.0` when the sum is close to zero; all balance updates use it, so no `1e-17` dust |
| `clippy::float_cmp = "deny"` | `==` on floats needs a local `#[allow]` with a reason |

### 3.5 Errors versus rejections

- `Err(Error::{Broadcast, FlexLen, UnknownLevel, LevelWidth, Invariant})` means an invariant broke (negative cash, bad parameter); the run stops.
- **A rejected order is never an `Err`**: it is an `OrderResult` with `status = Ignored | Rejected` and a `status_info` reason (§7.6), recorded in logs (§9.4).

### 3.6 Domain model (phasor-model)

| Item | Detail |
|---|---|
| Execution enums (`enums.rs`) | `#[repr(i8)]`, discriminants pinned by a test (records store integers): `SizeType`, `Direction`, `OrderSide`, `OrderStatus`, `StatusInfo` (15 reasons), `LeverageMode`, `CashFlowKind`, plus signal, stop and record enums with vectorbt semantics |
| Ids (`ids.rs`) | `Symbol`, `Venue` (`Arc<str>`), `InstrumentId` shown as `SYMBOL.VENUE`; not interned yet (§17.4) |
| `BarType` (`bar.rs`) | `SYMBOL.VENUE-STEP-AGGREGATION-PRICE-SOURCE`, parsed with `rsplitn(5, '-')`; the catalog key (§4.1) |
| Fixed point (`types.rs`) | `Price { raw: i64 }`, `Quantity { raw: u64 }`, 9 decimals, Nautilus shape; for phase 2 (phase 1 is `f64`) |

Execution semantics follow vectorbt; value and identifier types follow NautilusTrader.

## 4. Data layer: phasor-data and phasor.data

```mermaid
flowchart LR
  F["files<br/>{root}/data/{name}/{key}/*.csv, *.parquet"] --> L["load: 65,536-row batches<br/>project to input"]
  L --> D["decode (Rust or Python callback)"]
  D --> O["project to output<br/>check times, instruments"]
  O --> W["keep available_time ∈ [start, end)"]
  W --> P["prepare → BarPanel"]
  W --> A["align → T × instruments"]
```

`crates/phasor-data/src/lib.rs` never downloads and never writes; downloaders are
in `examples/` (`binance.py`, `fetch.py`, `download_binance_vision.py`).

### 4.1 Catalog layout

`<root>/data/<name>/<key>/*.csv | *.parquet`. `name` is the dataset (`bars`,
`funding`, `news`); `key` is a `BarType` for bars or an `InstrumentId` otherwise.
`catalog(root, name, keys)` lists files sorted. Python's default root is
`~/.cache/phasor/catalog`.

### 4.2 Schema and loading

`DataSchema { name, input, output, event_time, available_time, instrument }`:

| Field | Meaning |
|---|---|
| `input` / `output` | Arrow schema read from files / after decoding |
| `event_time`, `available_time` | `UInt64` UTC ns; **every filter and join uses `available_time`** — this is what prevents look-ahead on late-published data |
| `instrument` | `Source` (from the key), `Columns { symbol, venue }` (per row), or `Global` |

`load(schema, items, start, end, decode)` returns `Dataset { schema, keys, batches }`.

### 4.3 Bars to a panel

`Dataset::prepare()` → `BarPanel { time, bar_types, values: OhlcvPanel }`. Time
axis = sorted union of `available_time`; missing bar = NaN; duplicate bar = error.

### 4.4 Point-in-time alignment of auxiliary data

`Dataset::align(time, instruments, field, window, empty)`:

| Mode | Value at time `t` |
|---|---|
| no window (as-of) | last value with `available_time <= t` |
| `(width, agg)`, agg = `Sum`, `Count` or `Mean` | aggregate of `(t - width, t]`, non-finite skipped, `empty` if none |

Global events broadcast to every instrument. Python: `Dataset.asof(panel, field=…)`,
`Dataset.window(panel, field=…, window="30m", agg="mean")`; see `examples/multi_data.py`.

### 4.5 The Python data API

`crates/phasor-py/python/phasor/data.py`: `DataSchema(...)`, `files({key: path})`,
`Catalog(root, schemas).source(name, keys)` → `.load(start, end)` / `.prepare()`.
`BarPanel` exposes `(T, S)` Fortran arrays, `instruments`, `coverage()`. Loading,
`prepare` and `align` release the GIL; a Python decoder re-acquires it per batch.

## 5. Factor expressions: phasor-expr

```rust
let factors = FactorSet::compile([("trend", "$close / Mean($close, 20) - 1")])?;
let values = factors.evaluate(&FactorInputs::from_ohlcv(&panel)?)?;
let trend: &Matrix = values.get("trend").unwrap();   // time × symbol
```

A factor is information, not a decision; turning it into orders is §6.

### 5.1 The language

- **Fields** `$name`: OHLCV from `from_ohlcv`, anything else via `with_field(name, &[f64])`.
- **Operators**, low → high: `|`, `&`, comparisons, `+ -`, `* /`, unary, `**` (right-assoc). Booleans are `1.0`/`0.0`.

| Group | Functions | Notes |
|---|---|---|
| Elementwise | `Abs Sign Log Not`; `Add Sub Mul Div Power Gt Ge Lt Le Eq Ne And Or`; `Greater Less`; `If(c, a, b)` | operator and function spellings are the same node |
| Shift | `Ref(x, n)`, `Delta(x, n)` | row-based; negative `Ref` reads the future → `uses_future()` |
| Smoothing | `EMA(x, p)` | `p < 1` alpha, `p >= 1` span, `0` expanding |
| Rolling `(x, N)` | `Mean Sum Std Var Max Min Med Mad Count Skew Kurt WMA Rank IdxMax IdxMin Slope Rsquare Resi` | `Rank` is time-series; `IdxMax/Min` 1-based |
| Rolling `(x, N, q)` | `Quantile` | linear interpolation |
| Pairwise `(x, y, N)` | `Corr Cov` | |

Window rules: `min_periods = 1`, `N = 0` is expanding, NaN stays NaN; parameters
must be literals. `alpha158()` / `alpha360()` compile Qlib's feature sets (need an
explicit `vwap`; no normalization or labels). Not supported yet: cross-sectional
operators, cross-instrument references, masks (§5.7).

### 5.2 Parsing

`parse.rs`: source ≤ 16 KiB, Pratt parser, depth ≤ 128, `validate` checks names
and arity. The `Expression` tree is kept for `required_fields()`, `uses_future()`
and the Polars backend.

### 5.3 Compiling to a dependency graph

![Three factors compile into one graph: shared nodes are stored once, fields take no slot, scratch slots are reused after their last reader](img/en/graph.svg)

`graph.rs` builds one `Graph` for the whole set:

1. **Hash-consing** on `(Op, inputs)`: `Ref($close, 1)` used by dozens of Alpha158 factors is one node; `a+b` and `Add(a,b)` are one node.
2. **Compile-time validation** into typed ops (`Ref(i64)`, `Rolling(kind, Window)`, …); errors name the factor.
3. **Constant folding** of all-literal elementwise nodes.
4. **Dependency order**: nodes are appended after their inputs.
5. **Views**: `Ref(x, k)` with `k ≥ 0` is not computed; it is `x` read `k` rows late, and elementwise operators read it through the offset (Alpha360 is 354 such nodes).
6. **Slot scheduling** (`Graph::schedule`): a slot is freed after its last reader; a node never reuses an input's slot; a node nothing reads is written straight into its factor's output and takes no slot.

Alpha158 → 357 nodes, 17 slots, 148 written directly; Alpha360 → 722 nodes, 1 slot.

### 5.4 Native evaluation

![Native evaluation: each symbol column is one rayon task; each worker thread owns graph.slots scratch series and writes into disjoint column slices of every output](img/en/evaluate.svg)

`eval.rs:evaluate`:

1. Resolve all fields first (the parallel part has no error path).
2. Allocate one buffer per output separately, so pages are zeroed lazily by the writing thread (one cloned zero buffer cost 350 ms serially).
3. Split every output into per-column `&mut` slices; task `c` owns column `c` of every output — no locks, no `unsafe`.
4. `into_par_iter().for_each_init`: `run_column` walks the nodes; fields are borrowed, literals broadcast, elementwise ops dispatch outside the loop (`binary_series`), time-series ops call §5.5.

Intermediates are one symbol's series (~20 KB at 2,520 rows), so peak memory is
essentially the outputs. `each_symbol_evaluates_exactly_as_it_would_alone` pins bit-identity.

### 5.5 Kernels

![O(1) rolling accumulator: push the entering row, pop the leaving row; rebuild every N rows, shifted sums, exact constant windows](img/en/window.svg)

| Operators | Kernel | Cost / row |
|---|---|---|
| `Mean` | prefix sums (`phasor_generic::rolling`) | O(1) |
| `Max Min` | monotonic deque | amortized O(1) |
| `Sum Std Var Skew Kurt WMA Slope Rsquare Resi Corr Cov` | incremental accumulators (`window.rs`) | O(1) |
| `Quantile Med Rank Mad` | sorted ring for windows ≤ 256, else Fenwick tree over sorted positions (`order.rs`) | O(window) shift / O(log n) |
| `IdxMax IdxMin` | monotonic queue (`order.rs:rolling_arg_extreme`) | amortized O(1) |
| `Count` | `Count` accumulator (`window.rs`) | O(1) |
| `EMA` | recurrence | O(1); `EMA(x, 0)` O(n) |

Why each accumulator trick exists: **rebuild every window** bounds rounding drift
to two windows at O(n) total; **shifted sums** avoid cancellation of large
squares; **constant-window detection** gives exactly zero variance where Qlib tests
`== 0`. The Fenwick tree works on integer positions, so `Quantile/Med/Rank` are
bit-identical to sorting. Every kernel is tested against a full rescan (`1e-9`)
on NaN runs, constant runs and large levels; Qlib fixtures pin the end result (§14.3).

### 5.6 The Polars backend

Feature `polars`: `set.evaluate_with(&inputs, &PolarsBackend)`. Long frame,
`.over(symbol)`, batches of 64 factors, `rolling_map` for Qlib-specific ops. Use:
an independent cross-check (Qlib fixtures run on both).

| Panel | Workload | Native | Polars | Ratio |
|---|---|---:|---:|---:|
| 1024 × 16 | 4 elementwise | 0.3 ms | 5.0 ms | 15× |
| 2520 × 200 | 6 rolling (w=20) | 31 ms | 102 ms | 3.3× |
| 2520 × 200 | Alpha158 | 0.60 s | 6.2 s | 10× |
| 2520 × 200 | Alpha360 | 0.41 s | 2.7 s | 6.7× |
| 2520 × 500 | Alpha158 | 1.5 s | 19.4 s | 13× |

(4 threads, best of 3.) Costs: regrouping per operator, O(window) UDFs, no
sharing across batches, `Option<f64>` conversions.

### 5.7 Memory, limits and planned work

| Alpha158 (4-core dev container) | Result |
|---|---|
| 2520 × 200 | ~0.8–1.0 s |
| 2520 × 16 | ~75 ms (160 ms before the graph) |
| peak RSS 2520 × 500 | ~1.6 GB, almost all outputs |

Limits: all outputs are held at once (5,000 × 2,520 would need ~16 GB → batched
output); per-symbol parallelism is valid only while every op reads one symbol
(cross-sectional ops need stages). Both in §17.2.

## 6. Signals

**The rule that matters: delay.** A factor from bar `t`'s close is known after
bar `t`; trading on it at `t` is look-ahead. Every helper delays by default or
takes the delay as a parameter (`crates/phasor/tests/factor_path.rs`).

### 6.1 `SignalSweep` (Rust)

`phasor::sweep::SignalSweep::from_factor((name, &Matrix), symbols, cases, delay, rule)`:
`rule(factor[row - delay, symbol], &params) -> (entry, exit)` for every case ×
symbol; first `delay` rows and non-finite scores emit nothing; columns labelled
`factor`/`case` (repeat) × `symbol` (tile). `args(&swept_close)` returns a
ready `FromSignals`. Example: `crates/phasor/examples/factor_sweep.rs`.

### 6.2 phasor-signals

Column-major `&[bool]` utilities: `clean_enex` (strict alternation), `generate_exits`,
`exit_after`, `exit_on`, `generate_alternating`, ranks (`signal_rank`,
`partition_rank`, …), ranges → `RangeRecords`; seeded random signals (`random_by_prob`, `random_n`, `random_entries_exits`), each draw a function of `(seed, row, col)`; ML targets in `labels` (`fixed_horizon_returns`, `trend_labels`, `triple_barrier`, `pivot_labels`), which read the future and must never be signals.

### 6.3 Python function strategies

```python
@phasor.strategy
def ma_cross(data, fast, slow):
    f = phasor.factors(data, fast=f"Mean($close, {fast})", slow=f"Mean($close, {slow})")
    return phasor.crossed_above(f["fast"], f["slow"]), phasor.crossed_above(f["slow"], f["fast"])

pf = ma_cross.sweep(panel, params=[{"fast": 5, "slow": 20}, …], threads=4)
```

`factors` rejects expressions that read the future. `.sweep(..., signal_delay=1)`
calls the function per parameter set, delays, concatenates columns
(`param_idx * S + symbol`), passes `column_map = tile(arange(S), n_params)`, sets
`group_lens = [S] * n_params` with `cash_sharing=True`, and calls `from_signals`.

### 6.4 Indicators

`phasor-indicators`: `ma mstd bbands rsi stoch macd true_range/atr obv` over
parameter grids with the §3.1 layout (`column_of = comb * n_input + input_col`)
and shared-intermediate caches. Rust only, single-threaded.

## 7. Execution kernel: phasor-exec

`execute_order(state, order, reject_draw)` in `crates/phasor-exec/src/kernel.rs`
executes one order against one account at one bar. Both loops call it, and phase 2 will.

### 7.1 State and request

| Type | Fields |
|---|---|
| `ExecuteOrderState` | `cash, position (signed), debt, locked_cash, free_cash` |
| `ProcessOrderState` | + `val_price, value`, record counters |
| `Order` | `size=+inf, price=+inf, size_type=Amount, direction=Both, fees, fixed_fees, slippage, min_size=0, max_size=+inf, size_granularity=NaN, leverage=1, leverage_mode=Lazy, account_type=Cash, initial_margin=NaN, margin_basis=Notional, cash_limit=+inf, reject_prob, lock_cash, allow_partial=true, raise_reject, log` |
| `OrderResult` | `size, price, fees, side, status, status_info` |

`cash` is own cash: borrowed money is never in it. `debt` is what the column
owes: a short's proceeds at entry price, or what a leveraged long borrowed.
`locked_cash` is the own cash the position ties up: a long's paid-in share of its
cost, a short's collateral (`value / leverage` at entry). `free_cash` is own cash
net of what shorts tie up, so opening a short moves it by
`proceeds − short_value − short_value / leverage`, the reference's
`proceeds − 2 × short_value` at leverage 1. All of it is path-dependent, so it is
explicit state. Without leverage a long has no debt and a short's `locked_cash`
equals its `debt`, the only state the reference can describe (§7.7). A margin
column reads `debt` and `locked_cash` as cost basis and margin posted (§7.8).

### 7.2 Validation

1. Zero-snap state values that are `is_close` to 0.
2. NaN size / NaN price → `Ignored` (before validation).
3. `validate_bar`: cash not NaN and ≥ 0 (below 0 allowed in a leveraged or margin account, §7.7–7.8), finite non-negative `debt` and `locked_cash`, finite position, price > 0, direction consistent with position.
4. `param_violation`: fees finite, slippage ≥ 0, sizes positive, `leverage` finite and ≥ 1, `reject_prob ∈ [0,1]`, `cash_limit ≥ 0`; a margin order's `initial_margin` (§7.8).

`locked_cash` is not zero-snapped: it is only read in proportion to a position, and
the kernel leaves no residue in it. `debt` and `locked_cash` are tested together
(`(debt + locked_cash).is_finite()` and `debt.min(locked_cash) ≥ 0`), with the
exact checks in a cold function: on aarch64 each `!x.is_finite() || x < 0` compiles
to an integer classification of about 17 instructions, and this runs every bar.

Violations are `Err(Invariant)`. `ValidatedOrder` caches step 4 per column and
swaps only per-bar fields (`set_bar`): +30% sparse / +22% dense in `benchmarks/README.md`.

### 7.3 The size cascade

![Size cascade: ShortOnly flip, TargetPercent → TargetValue, Value → Amount, TargetAmount → Amount, −inf → Percent(−1), Percent → ±inf; the sign dispatches buy or sell; optional random rejection](img/en/cascade.svg)

Each stage rewrites the size type; only `Amount` reaches dispatch. Zero and NaN
take the sell branch, as in the reference.

### 7.4 Buying and selling

| | Buy | Sell |
|---|---|---|
| price | `price × (1 + slippage)` | `price × (1 − slippage)` |
| cap | cash (or `lock_cash` closed form over `free_cash`), × `percent`; `ShortOnly` covers only | `LongOnly` caps at position; shorts bounded by `free_cash` + long proceeds |
| fees | inside the cash cap; if unaffordable back-solve `(cash_limit − fixed_fees) / (1 + fees)`, then **granularity again**; leveraged: §7.7 | `CantCoverFees` if proceeds net of fees < 0 |
| checks | `max_size`, `SizeZero`, `MinSizeNotReached`, `PartialFill`, `NoCashLong` / `NoCashLeverage` | same + `NoOpenPosition`, `NoCashShort` |
| debt | covering releases debt and collateral, adds `debt_diff + locked_diff` to `free_cash` (`2 × debt_diff` at leverage 1); a leveraged long borrows into `debt` | a new short adds debt, reserves `short_value + short_value / leverage`; selling a long repays its share of debt and frees its share of `locked_cash` |

### 7.5 Why the tolerance matters here

Affordability is `is_close_or_less(total_req_cash, cash_limit)`, not `<=`. They
differ only inside `1e-9`, and a mutation swapping them first survived.
`size_granularity` turns that into a whole unit (5.0 vs 4.0), so boundary
fixtures built with `math.nextafter` now catch it (§14.4).

### 7.6 Outcomes and rejection reasons

`OrderStatus`: `Filled | Ignored | Rejected`. `StatusInfo` (15): `SizeNaN PriceNaN
ValPriceNaN ValueNaN ValueZeroNeg SizeZero NoCashShort NoCashLong NoOpenPosition
MaxSizeExceeded RandomEvent CantCoverFees MinSizeNotReached PartialFill
NoCashLeverage`; the first 14 are the reference's, `NoCashLeverage` (14) is a
leveraged buy with no own cash to put up.
`raise_reject` turns a rejection into an error. `reject_prob` takes a
caller-supplied draw. Both loops compute it from `(seed, row, col)` with
SplitMix64 (`phasor_core::random::uniform`, `crates/phasor-core/src/random.rs`),
only when the probability is non-zero, so it does not depend on the thread
count or the grouping; a custom loop that calls the same function rejects the
same orders. The random signals (§6.2) and the synthetic prices draw through
the same module.
`cash_limit` (not in the reference, not in the log schema) caps the cash a buy
may spend, applied before `percent`; sells and shorts are unaffected.

### 7.7 Leverage

`Order::leverage` (≥ 1, default 1) is buying power per unit of own cash; not in the
reference, which has only leverage 1. At 1 every fill is the reference's to the
bit, which the parity fixtures check; the leveraged paths are separate code, out
of line where they would otherwise sit on the hot path.

| | Without leverage | `leverage = λ > 1` |
|---|---|---|
| long buy | own cash pays notional + fees | own cash pays `1/λ` of the long part, all of any short being covered, and every fee; the rest is borrowed into `debt` |
| `leverage_mode` | — | `Lazy` (default): own cash first, up to the cap, borrow the rest (nothing when it all fits). `Eager`: always borrow `1 − 1/λ` |
| `percent` | of own cash | of own cash, then levered: 100% at 3× buys three times the cash |
| long sell | proceeds to cash | proceeds repay the long's share of `debt` first; its share of `locked_cash` is freed |
| short | reserves proceeds + value | reserves proceeds + `value / λ` (λ = 2 is Reg T's 150%); with `lock_cash` or a percentage the size limit is `(free_cash − fixed_fees) / (price × (1/λ + fees))` |
| negative cash | invalid state | a long sold below its debt leaves the account owing; the account can sell, and its buys are rejected (`NoCashLeverage` if the order is leveraged, else `NoCashLong`) |

Interest on what a long borrowed and a short's borrow fee are holding charges
of the loop (§8.6). Maintenance margin and liquidation apply to margin
columns only (§8.7); a leveraged cash column is not margin-called yet.
`CallSeq::Auto` sorts by `approx_order_value`, which does not account for
leverage.

### 7.8 Margin accounts

`Order::account_type` says how a column pays for its trades: `Cash` (the
default, everything above) or `Margin`, for futures, perpetuals and CFDs. It is
a property of the column for the whole run, so one that changes down a column
is an error; one group can hold spot columns beside margin columns and share
their cash, which is how a spot-long, perpetual-short pair is one account. Not
in the reference. A margin column reads the same five state fields
differently, and `margin_trade` (`kernel.rs`, cold, out of line) fills it:

| | Cash column | Margin column |
|---|---|---|
| opening | a long pays its price, a short reserves proceeds + `value / λ` (§7.7) | either side posts initial margin out of `free_cash` and pays its fees; nothing is borrowed or received |
| `debt` | what a long borrowed, a short's proceeds | cost basis: `abs(position) ×` average entry price |
| `locked_cash` | own cash the position ties up | initial margin posted, still in `cash` |
| closing | proceeds to cash, debt repaid | realizes profit against `debt / abs(position)`, releases that share of the margin |
| each bar | nothing | the loop settles the profit since the last bar into `cash` and `free_cash` and moves the basis to the valuation price |
| `free_cash` | cash net of what shorts tie up | equity less every margin position's margin |

- **How much margin.** `initial_margin` per unit opened, in `margin_basis`:
  `Notional` (default) is a fraction of the notional at the fill price, and
  `NaN` (default) means `1 / leverage`, so `leverage = 10` alone is a 10×
  perpetual; `Unit` is cash per unit of size, as a futures exchange publishes
  it per contract, and must be set. The margin is fixed at the fill: a later
  value applies to later fills only. Both are flexible per bar.
- **How much may open.** Closing is always allowed. Opening is capped at
  `(free_cash + freed − fixed_fees) / (unit_margin + price × fees)`, where
  `freed` is what closing the whole opposite position would realize and
  release, so a reversal opens with it; `cash_limit` caps the budget, and
  `percent` takes its share of what closes plus what may open. Out of free cash
  the opening is `NoCashLong` / `NoCashShort`; `LongOnly` and `ShortOnly`
  only close the other side (`NoOpenPosition`). `leverage_mode` and
  `lock_cash` do not apply: nothing is borrowed, and every position reserves
  its margin anyway.
- **Negative cash.** Fees come out of cash and a loss can exceed it, so cash may
  go below zero, as in a leveraged account; the account can still close and
  its openings are rejected, unless a maintenance margin liquidates it
  first (§8.7).
- **Validation.** `param_violation` adds two checks for margin orders:
  `initial_margin` is `NaN` or finite and > 0, and set when the basis is `Unit`.
  `ValidatedOrder` marks a margin order `in_levered_account`.

Settlement is the loop's (§8.4), and it is not a cash flow: it moves money
between the position and the cash without changing the equity, so it leaves
no record. The analysis rebuilds the same equity from the fills alone (§10.2).

`margin_mode` (`Cross`, the default, or `Isolated`, per column for the run)
says whose margin a position draws on. A cross column is settled as above.
An isolated column is never settled into the account's cash: its `debt` stays
the cost basis at entry, its profit or loss stays with the position until it
closes, and so the account's free cash excludes it, profit and loss alike.
The kernel trades both the same way. Maintenance margin and liquidation are
§8.7.

## 8. Simulation loops: phasor-sim

Two loops (orders, signals), each plain / logged / serial / parallel.

### 8.1 `from_orders`

![One bar of a shared-cash account: pass 1 resolves prices and stops for every column, the bar-open value is computed once, CallSeq orders execution, pass 2 executes and writes records and logs](img/en/bar-loop.svg)

`FromOrders<'a>` holds every input as a `FlexArray` (one element = one order
request, NaN size = none). Per group (`simulate_group`): build `ValidatedOrder`s
once per column; per bar resolve prices (`+inf` → close, `-inf` → previous
close), compute the bar-open value, resolve the call sequence, execute. With
`update_value` the value is re-marked after each fill. Entry points:
`simulate_from_orders[_logged][_parallel]`, `Portfolio::from_orders(&args, threads)`.

### 8.2 `from_signals`

![from_signals per bar and column: armed stops are tested first (gap → open, touch → level); a hit replaces the signals; otherwise read signals and resolve conflicts; signals_to_size builds the order](img/en/signals.svg)

- Defaults: `init_cash = 100`, `LongOnly`, `size = +inf`, `min_size = 1e-8`, conflicts `Ignore`, `upon_opposite_entry = ReverseReduce`, stops off, `stop_exit_price = StopLimit`, `upon_stop_update = Override`.
- Signal conventions (OR-merged): `entries/exits + direction` (in `Both`, exit = short entry), or four explicit arrays.
- Conflicts: `resolve_signal_conflict` → `resolve_dir_conflict` → `resolve_opposite_entry`.
- `signals_to_size` accepts only `Amount | Value | Percent`.
- The stages in `signals.rs` are pure functions, tested exhaustively (§14.3).

### 8.3 Groups, cash sharing and call order

| Item | Detail |
|---|---|
| `Groups { lens, starts, of_col }` | `ungrouped(n)` default; `from_lens` validates coverage; cash from `init_cash` at the first column |
| `CallSeq` | `Default` (layout), `Auto` (by `approx_order_value`, stable, NaN last → sells first), `Explicit(&[usize])` |
| Parallel unit | the group; one portfolio of every symbol is one unit on one thread |
| Record order | shared groups emit in execution order; analysis re-sorts by `(col, idx)` |

### 8.4 Defaults, logging and sinks

- `DEFAULT_MIN_SIZE = 1e-8` (reference) vs kernel default `0.0`; logs found the difference (§9.4).
- Logged variants write one row per order *considered*; off by default (a log row is ~5× an order record). A test asserts logging does not change orders.
- Both loops build each column's `ValidatedOrder` once (a second, slippage-free one for stops resting at their level in `from_signals`) and rebuild per bar only when a parameter varies by row; a bar with no signal and no armed stop skips sizing.
- Both loops are generic over `SinkBuffer` (§9.3).
- Leverage: `any_levered` decides once per run whether any column's `leverage` exceeds 1. Each loop has a `const LEV: bool` copy, as `FLOWS` (§8.5), so a run without leverage has no code for it. With it, every order is marked `in_levered_account()` (accepts negative cash), the bar's value subtracts each long's debt, an `update_value` re-mark subtracts the debt a fill added, and each fill records its `debt` and `locked_cash` (§9.1). A column at leverage 1 in a leveraged run fills exactly as in a run without one.
- Holding charges (§8.6) also put a run in the `LEV` copy: a charge is owed whatever the balance, so the account must accept cash below zero, and their code stays out of a run without them.
- Margin columns (§7.8, `crates/phasor-sim/src/margin.rs`): `any_levered` also counts them, so they run in the `LEV` copy, which reads each group's account types once (`margin_columns`). Every bar, once the valuation price is resolved and before the group is valued, `settle` moves each margin position's profit since the last bar into the group's `cash` and `free_cash` and its cost basis to the price; `from_signals` does it on bars with no signal too, because a shared account's next order sizes from it. The group's value counts a margin position at `unsettled` (its profit against the basis) rather than `position × price`, and the `update_value` re-mark subtracts the basis a fill added, as it does a leveraged long's debt. A cash column in the same run keeps its §7.7 bookkeeping.

### 8.5 Cash flows outside fills

Both loops take `cash_deposits`, `cash_dividends` and `cash_earnings` (`crates/phasor-sim/src/cash.rs`).
The defaults are a scalar zero, detected once per group, so a run without them
does no extra work per bar.

| Input | Booked | Read at | Record kind |
|---|---|---|---|
| `cash_deposits` | bar open, before prices are resolved and orders sized | the group's first column, like `init_cash` | `Deposit` |
| `cash_dividends` | bar open, after the deposit; per share × the position held before the bar's orders (a short pays) | each column; source-shaped through `column_map` in Python | `Dividend` |
| `cash_earnings` | bar close, after every order, including bars with no signal | each column, in layout order | `Earning` |

- A deposit is in the bar's valuation, so a target-sized order on the same bar invests it.
- A negative amount is capped at `max(free_cash, 0)`, so cash never goes below zero; the amount actually applied is what is recorded.
- `NaN` means no flow; `±inf` is an error.
- vectorbt 1.1.0 has no counterpart, so there is no fixture. `crates/phasor-analysis/tests/cash_flows.rs` checks hand-calculated accounts, checks that every logged order's cash and free cash equal the balances rebuilt from records (§10.2), ungrouped and shared, and checks thread invariance.

### 8.6 Holding charges

What holding a position costs or earns (`crates/phasor-sim/src/holding.rs`):
four charges, booked per column at the bar's close after its orders and its
`cash_earnings`, on the position the orders left, quiet `from_signals` bars
included. Not in the reference, and not in PRO, which leaves funding to a
callback.

| Input | Charged on | Amount | Record kind |
|---|---|---|---|
| `funding_rate` | any position | `−position × price × rate`: longs pay a positive rate, shorts receive it | `Funding` |
| `long_financing_rate`, `short_financing_rate` | any position | `−|position| × price × rate`, the rate of the position's side | `Financing` |
| `debt_rate` | a cash column's long | `−debt × rate`, on what it borrowed (§7.7) | `Interest` |
| `borrow_rate` | a cash column's short | `−|position| × price × rate` | `BorrowFee` |

- `price` is `mark_price`, or the close where that is `NaN` (the default), or the column's last valuation price where both are; with none, the charge is skipped, as settlement is. The mark price is the charges' notional only: the loop still values and settles at `val_price`, and the analysis at the close.
- A positive rate is a cost to the holder. A perpetual's funding is the case where the short's rate is minus the long's, so it is one input; financing has two because a broker's swap rates for the two sides differ and can both be costs. A margin column borrows neither cash nor shares, so it pays funding and financing but no interest or borrow fee.
- **Every rate is per bar**, for the time until the next bar: the loop has no clock. `phasor.rates.per_bar(annual, index, days_per_year=365)` converts from the bars' timestamps, so Friday's daily bar charges three days and the last bar nothing. A funding rate is already per settlement: it goes on the bar whose close is the funding time, `NaN` elsewhere.
- **A charge is not capped.** Unlike an earning it is owed whatever the balance, so any of these inputs runs the accounts in the `LEV` copy (§8.4): cash may go below zero, after which an account can close and not open, and the fills record their balances. A column at leverage 1 fills as it would without them; `crates/phasor-sim/tests/holding.rs` checks that bit for bit.
- `NaN` or zero is no charge and leaves no record; an infinite rate is an error. The defaults are scalar zeros, detected once per run.
- Each charge is a `CashRecords` row with the amount applied, so the analysis counts it in cash, free cash, value and returns with nothing new (§10.2). `crates/phasor-analysis/tests/holding.rs` checks that the rebuilt equity is, bar by bar, the value the loop sized against less the bar's fees plus the bar's charges, with leverage, margin columns and shared accounts.


### 8.7 Maintenance margin and liquidation

An exchange closes a margin position once the account can no longer carry it
(`crates/phasor-sim/src/liquidation.rs`). Not in the reference, nor in PRO.
Every bar, once its prices are resolved and its cross columns settled and
before anything is valued or ordered, each account with a margin column and a
`maintenance_margin` is tested on the positions it carried in; a position is
tested from the bar after it opened, as a stop is.

- **The path.** Each held column moves from its *start*, the bar's open, to
  its *check* price: `mark_price` where given, else the bar's adverse extreme
  (the low for a long, the high for a short; missing OHLC falls back to the
  close). Moved together by `α ∈ [0, 1]`, the equity `E(α) = cash + Σ
  (position × p(α) − owed)` and the requirement `M(α) = Σ maintenance_margin ×
  |position| × p(α)` (or `× |position|` per unit, in `margin_basis`) are
  linear. If `E(1) ≥ M(1)` nothing happens; otherwise the account is
  liquidated at `α = g(0) / (g(0) − g(1))` with `g = E − M`, or at the open
  when `g(0) ≤ 0` — a gap. With one position this is the textbook liquidation
  price.
- **Cross**: the test is the account's. Cash columns count in the equity and
  are never closed; every cross column that carries a maintenance margin is
  closed together, in layout order, each at its own point of the path.
  Without a mark price each leg of a hedge is tested at its own extreme,
  which no single instant reaches, so a hedged account wants a mark price.
- **Isolated**: the test is the column's alone, `E(α) = locked_cash +
  position × p(α) − owed`, and the account's test leaves its margin and
  position out.
- **Stops** (`from_signals`): a stop that fired on the bar was hit on the way,
  so its column is tested at the less adverse of its check price and the
  stop's level: a stop inside the liquidation price saves the position, one
  beyond it does not. A liquidated column's pending order is dropped and its
  stops cleared, since it was sized against a position that is gone; in
  `from_orders` the bar's orders still execute, being requests for the bar.
- **The fill** goes through the kernel as `TargetAmount(0)` at the
  liquidation price, no slippage, `liquidation_fee × notional` as its fees,
  flagged `liquidation` in the order records and the logs.
- **Write-off.** An isolated column whose closing returns less than nothing,
  or a cross account left with no cross or cash position and less cash than
  its isolated positions' margin, has lost more than it had: the shortfall is booked back as a positive
  `CashRecords(kind = Liquidation)`, as an exchange's insurance fund absorbs
  it. The equity stops at zero and the return at −100%.
- **Validation.** `maintenance_margin` is `NaN`/0 (none), or finite, ≥ 0 and
  below 1 under `Notional`; `liquidation_fee` is finite and ≥ 0. Errors name
  the row and column.
- **Cost.** `any_levered` already sends margin runs to the `LEV` copy; the
  test is an out-of-line call behind a flag fixed per group, so a margin run
  without a maintenance margin does not pay for it, and a run with no margin
  column has no code for it at all.

`crates/phasor-sim/tests/liquidation.rs` works the cases by hand (the exact
price, a gap and its write-off, a short at the high, a stop inside and beyond
the level, a cross account closing together, an isolated column alone and its
capped loss, a hedge at extremes and at a mark, threads);
`crates/phasor-analysis/tests/liquidation.rs` checks that the rebuilt equity
is the loop's on every bar of a run that liquidates and writes off.

### 8.8 One bar, in order

Both loops run each account's bar in this order; `from_signals` adds the
stop and signal steps. Each step reads what the steps before it left.

1. **Open**: the deposit, then dividends on the position carried in (§8.5).
2. **First pass, per column**: the order price and the valuation price are
   resolved. In `from_signals`, armed stops are tested against the bar's
   open, high and low (a gap fills at the open), trailed, and the signals are
   read and sized. Cross margin columns settle at the valuation price (§8.4).
3. **Liquidation**, on the positions carried in, before anything is valued
   (§8.7). A stop that fired in step 2 is credited.
4. **Value and order**: the group is valued once at the valuation prices,
   and the call sequence orders the columns (§8.3).
5. **Second pass**: the orders execute, stop exits among them, at their stop
   level or at the open after a gap.
6. **Close**: `cash_earnings`, then the holding charges, on the position the
   orders left (§8.5, §8.6).

So a stop that fills at the open still comes after the open's deposit and
dividend: the dividend is owed to the position the stop then closes, as on an
ex-date, and the deposit is in the cash the bar's orders size from. A
position opened on a bar is first tested for its stops and for liquidation on
the next one, and first charged at the close of the bar it opened on.

### 8.9 Contract multiplier

`multiplier` is what one unit of position is worth per unit of price: 50 for
an E-mini S&P 500 future, 1 (the default) for a share. Per column, and
constant down it (`multipliers` in `crates/phasor-sim/src/lib.rs` refuses one
that changes, and one that is not finite and above 0).

- **Where it is applied.** A multiplier other than 1 sends the run to the
  `LEV` copy (`any_levered` counts it), which runs a multiplied column at its
  prices times its multiplier. The kernel is unchanged: given `price × m`, a
  fill moves `size × price × m` of cash, and fees, `Value`/`Percent`/target
  sizes, a notional margin and the group's value all follow. Dividends are
  paid on `position × m` shares; the holding charges and the liquidation path
  multiply their price (§8.6, §8.7).
- **What stays in contracts or prices.** Sizes, `min_size`,
  `size_granularity`, `max_size` and a `Unit` margin are per contract. Stops,
  `price` and `val_price` are prices: `from_signals` keeps a column's
  valuation price unscaled, because its stops read it, and multiplies it
  where it values, settles, charges or executes; `from_orders` keeps it
  multiplied. The records and logs get the prices back, divided by `m` (to
  within a rounding error; exactly at 1), and each fill's `multiplier`.
- **Cost.** None on a run without one: the default run never reaches the
  `LEV` copy, and the copy itself only gains a multiply per price.

`crates/phasor-analysis/tests/multiplier.rs` checks the defining property on
random runs of both loops (cash and margin columns, leverage, shared
accounts, funding, dividends, liquidations): a run at `k` is the run at 1
with every amount-sized order `k` times larger, its sizes `k` times smaller
and everything in cash the same; plus a futures position by hand, the
refusals and threads.

## 9. Records: phasor-records

The contract between simulation and analysis, and between tiers. All struct-of-arrays.

### 9.1 Schemas

| Record | Fields | Row = |
|---|---|---|
| `OrderRecords` | `col, idx, size, price, fees, side`; `debt, locked_cash` after the fill, `margin` and `isolated` (the column's account type and margin mode), `liquidation` and `multiplier` (§8.9), in leveraged, margin or multiplied runs only (empty otherwise, and then every multiplier is 1; `push_balances` takes them as one `Balances`) | one fill |
| `LogRecords` | 46: before-state, `req_*`, `new_*`, `res_*`, `order_id`; the reference's 37 plus `locked_cash`, `new_locked_cash`, `req_leverage`, `req_leverage_mode`, `req_account_type`, `req_initial_margin`, `req_margin_basis`, `liquidation`, `multiplier` | one order considered, or one liquidation |
| `TradeRecords` | `col, size, entry_*, exit_*, pnl, ret, direction, status, parent_id, multiplier`; `pnl` is multiplied, `ret` is not | derived (§9.5) |
| `DrawdownRecords` | `col, peak/start/valley/end idx, peak/valley/end val, status` | derived (§9.6) |
| `RangeRecords` | start / end / status | phasor-signals ranges |
| `CashRecords` | `col, idx, amount, kind`; `kind` is `Deposit`, `Earning`, `Dividend` (§8.5), `Funding`, `Financing`, `Interest`, `BorrowFee` (§8.6) or `Liquidation` (§8.7) | one cash flow that was not a fill |

`CashRecords` travel inside `OrderRecords` as its `cash` field, so sinks
(`RecordSink::push_cash`), merges, sorting and the `Portfolio` constructors
carry them with no new plumbing; `len()` and `ids()` count fills only.

Ids are implicit (position after merge). Records are grouped by column with
ascending rows; shared groups are re-sorted by analysis.

### 9.2 Merging per-thread buffers

Buffers are concatenated in chunk order (`OrderRecords::concat`,
`Journal::concat`) and `order_id` is re-based, so output does not depend on the
thread count (diagram in §11.2).

### 9.3 Sinks

`RecordSink::push_order`, `LogSink` (no-op for plain records),
`SinkBuffer: RecordSink + LogSink + Send` (`with_capacity`, `merge`), implemented
by `OrderRecords` and `Journal { orders, logs }`. Traits let phase 2 reuse the
records without the preallocated storage. Buffers are preallocated to the worst
case; doubling growth cost ~15% of dense throughput.

### 9.4 Logs and what exposing them found

`reasons()` and `reason_counts(col, n_cols)` answer "why didn't it trade". Compare
logs field by field (NaN `res_*` break `==`). Diffing logs against the reference
found two bugs: default `min_size` `0.0` instead of `1e-8`, and `order_id` not
re-based across groups in the serial path.

### 9.5 Three views of trades

| View | One record per | Allocation |
|---|---|---|
| `entry_trades` | entry fill | exits FIFO |
| `exit_trades` | exit fill | entries averaged |
| `positions` | position | trades grouped by `parent_id` |

The views legitimately disagree on counts and win rates. Open trades are marked
at the last close; input must be sorted.

### 9.6 Mapped arrays and drawdowns

- `ColMap::build` is a stable counting sort with a zero-copy fast path when records are already contiguous.
- `MappedArray`: `count sum mean min max std idxmax idxmin reduce top_n_mask value_counts stack_expand`, skipping missing like the reference.
- `find_drawdowns` → one record per episode (`Active` / `Recovered`).
- `excursions` → per-trade MAE/MFE (price distance and return) over entry..=exit (open trades to the last bar), high/low falling back to close; `edge_ratio`.
- **Durations**: closed range `end − start`, open range `end − start + 1` (one rule for both would bias averages by up to a bar).

## 10. Analysis: phasor-analysis

### 10.1 `Portfolio`

Stores only order records, borrowed close, shape, groups, initial cash, optional
benchmark and `Scoring { ann_factor, risk_free, trades_type, incl_open }`.
Everything else is derived lazily into `OnceLock`s (so `Sync`, each series computed
once). Constructors: `from_records`, `from_grouped_records` (re-sorts shared
groups), `from_orders` / `from_signals` (run the simulation).

### 10.2 The rebuild chain

![Balances are rebuilt from order records alone: asset_flow → assets per symbol, cash_flow → cash per group, value = cash + assets × close, then returns and metrics](img/en/rebuild.svg)

- `cash_flow` and `free_cash_flow` add the `CashRecords` amounts to the fills' flows. Every kind but a deposit is part of the return, a holding charge included; `cash_flow_by_kind` (`Portfolio::cash_flow_by_kind`) gives one kind per bar and column.
- A deposit is not a return: `returns[t] = value[t] / (value[t−1] + deposit[t]) − 1`, the first bar measured from `init_cash + deposit[0]`. Without deposits the chain is unchanged, bit for bit.
- With deposits, an account's total return compounds the per-bar returns instead of `end / init − 1`, and drawdowns are found on `init_cash × Π(1 + r)` instead of the value curve, so a withdrawal is not a drawdown.
- Leverage: a fill's cash flow is its full price, so `cash()` is own cash less what longs borrowed and can go below zero, while `value()` stays equity. `free_cash` cannot be rebuilt from fills alone once a short's collateral depends on λ, so in a leveraged run `free_cash_flow` reads each fill's recorded `debt + locked_cash` as the short's reserve (a leveraged long reserves nothing). `gross_exposure` of a 2× long is therefore 2.
- Margin columns: their fills are charged their full price too, so `value = cash + position × close` is the equity the per-bar settlements add up to, and `value()` needs nothing new. `free_cash_flow` reads a margin fill's `locked_cash` as its reserve, on either side, and `Portfolio::free_cash` adds each margin column's `position × close` back into its account, which the account never paid: free cash is then equity less the margin posted, the simulation's own figure. `gross_exposure` counts the whole contract over that. An isolated column's profit is not free, so for it `free_cash` adds back its signed cost basis, the `debt` its last fill recorded, instead of `position × close`. A liquidation is a fill and a write-off a cash record, so neither needs anything new.
- Contract multiplier (§8.9): a fill's cash flow is `size × price × multiplier` and a position is worth `position × close × multiplier`, with each column's multiplier read off its fills (`series::multipliers`, `None` when all are 1, which leaves the chain as it was). The margin columns' `position × close` in `free_cash` is multiplied the same way.

### 10.3 Metrics

| Kind | Items |
|---|---|
| Returns (`metrics.rs`) | `total_return annualized_return annualized_volatility max_drawdown sharpe sortino calmar omega tail_ratio downside_risk value_at_risk cond_value_at_risk` |
| Benchmark (`benchmark.rs`) | `information_ratio beta alpha capture up_capture down_capture` |
| Rolling (`rolling.rs`) | rolling version of each |
| Trades | `TradeStats { count winning losing win_rate profit_factor expectancy sqn total_pnl best worst }` |
| Exposure (`Portfolio`) | `allocations` per symbol; `long_exposure short_exposure net_exposure gross_long_short` per account, against total account value (unlike `gross_exposure`, which divides by free cash plus the position); `position_coverage` |
| Robustness (`robust.rs`) | `norm_cdf norm_ppf probabilistic_sharpe expected_max_sharpe deflated_sharpe pbo_cscv` (Bailey & López de Prado; per-period Sharpe; PBO picks the in-sample winner by mean return, at most 16 blocks) |
| Events (`events.rs`) | `forward_paths` before/after each event (edge events kept, NaN-padded), `mean_path median_path hit_rate`; reads the future, analysis only |

### 10.4 The stats registry

`stats.rs`: 28 `DEFAULT_METRICS` with key, title, tags and compute function;
`benchmark_metrics()` adds four. `Select::{all, with_tags, keys, without_tags}`.
Titles and order match vectorbt's `Portfolio.stats()`, pinned row by row (§14.3).

### 10.5 Aggregating sweeps

- `traded_only(values)` masks accounts that never traded. **Pitfall:** zero volatility can give `+inf` Sharpe, which a naive argmax picks (`crates/phasor/tests/sweep.rs`).
- `group_by(columns, level, values, Reduce::…)` reduces per label; `best_column` names the winner (`window=20, symbol=BTC`).

## 11. Parallelism

### 11.1 Every parallel site

| Where | Mechanism | Unit |
|---|---|---|
| phasor-sim `simulate_into_parallel` | `std::thread::scope`, contiguous chunks | account group |
| phasor-expr `eval.rs:evaluate` | rayon `into_par_iter().for_each_init` | one symbol through the whole graph |
| phasor-expr Polars backend | Polars pool | lazy frames |
| phasor-py `lib.rs`, `expr.rs`, `data.rs` | `py.detach` (GIL released) | — |

Everything else is single-threaded.

### 11.2 The simulator

![Account groups are cut into contiguous chunks; each thread owns its sink and counters; buffers are concatenated in chunk order with ids re-based](img/en/threads.svg)

- `n_threads` clamped to `[1, n_groups]`; `Groups::chunks` cuts contiguous runs at fractions of the total column count, so every thread gets work and a wide group is its own run. No shared mutable state, no reduction.
- Buffers are preallocated to a fill bound (cells with a usable size; twice the set signal cells), not to `n_rows × n_cols`. Above 65,536 fills the merge copies the parts in parallel (`OrderRecords::concat`).
- Serial and threaded output are bit-identical (tested); the lowest failing chunk's error wins.
- Scoped threads, not a pool: they force `Sync` inputs and column-local state; tasks are 10⁴–10⁶ iterations, so scheduling cost is noise.

`cargo run --release --example scaling -p phasor-sim` (20,000 × 256, 4-core Xeon):

| Workload | 1 thread | 4 threads | Speedup |
|---|---:|---:|---:|
| sparse (1 fill / 20 bars) | 33 M elem/s | 121 M elem/s | 3.62× (90%) |
| dense (every bar) | 15 M elem/s | 25 M elem/s | 1.63× (41%) |

Dense is memory-bound (~245 MB of record writes); pure compute scales 3.96×.

### 11.3 Factor evaluation

See §5.4. Scaling is bounded by the number of symbols (16 symbols → at most 16
tasks) and by uneven per-symbol work.

### 11.4 Why threads and not SIMD for the loops

- Along time: impossible (`state[t] = f(state[t−1], bar[t])`).
- Across columns: the kernel branches (cascade, dispatch, fee back-solve, ~13 checks, 14 early exits, scatter writes); 4–8 lanes vs thousands of columns.

SIMD belongs in factor and analysis kernels, after layout and autovectorization.

### 11.5 The `Send` constraint

No `Rc`, no `RefCell`, no process-global state (only `OnceLock` caches in
`Portfolio`). Nautilus's `Rc<RefCell>` + message-bus singleton is exactly what
forces its sequential run. Phase 2 must use arena-and-index ownership, routing as
an engine field.

## 12. Python layer: phasor-py

### 12.1 Packaging

One wheel: Rust extension `phasor._phasor` (PyO3 0.29, `abi3-py39`, maturin) + package
`crates/phasor-py/python/phasor/`. Extras: `data` (pyarrow), `test` (pytest, vectorbt 1.1.0).

### 12.2 Arrays cross without copies — and must be Fortran-ordered

`array.rs:columns_of` borrows a 2-D `float64` array as a column-major slice and
**rejects C-ordered arrays** (reading row-major as column-major silently swaps
time and symbols). Wrappers call `np.asfortranarray`; tests assert borrowed arrays
are never written. 1-D arrays are ambiguous, so each call site states
`OneDim::{PerRow, PerColumn}`; simulation parameters treat 1-D as per column.

### 12.3 Simulation entry points

`phasor.from_signals(close, entries, exits, *, …)` and `phasor.from_orders(close, *, size, …)`
mirror the Rust structs: every parameter is scalar, per-column 1-D or `(T, C)`;
`cash_sharing` / `group_lens`; `call_seq` in `"default" | "auto"`; `column_map`
(prices `[T, S]`, signals `[T, C]`, `Portfolio.price_nbytes` reports retained
price memory); stops need `high` and `low`. `cash_deposits` and `cash_earnings`
read a 1-D array as one value per bar; a shared run's `cash_deposits` matrix is
`(T, n_groups)`, mapped onto columns without copying. `Portfolio.cash_records()`
returns what was applied. `leverage` takes the same shapes as the other
parameters, `leverage_mode` is `"lazy" | "eager"` (§7.7); in a leveraged run
`orders()` adds `debt` and `locked_cash`. `account_type` is `"cash" | "margin"`
or one of them per column, `initial_margin` takes the usual shapes, and
`margin_basis` is `"notional" | "unit"` (§7.8); a margin run's `orders()` also
has `margin`, and `Portfolio.free_cash()` returns the rebuilt free cash.
The holding charges (§8.6) take `funding_rate`, `long_financing_rate`,
`short_financing_rate`, `borrow_rate` and `mark_price` as market data, shaped
like `close` and read through `column_map`, and `debt_rate` as a parameter (1-D
is per bar); `Portfolio.cash_flows(kind)` returns one kind as `(T, C)`, and
`phasor.rates.per_bar` converts annual rates.

### 12.4 Other bindings

`phasor.FactorSet` (`compile`, `evaluate`, `required_fields`, `uses_future`),
`phasor.Expression`, `alpha158()`, `alpha360()` (native backend only);
`crossed_above`, `factors`, `@phasor.strategy`; `phasor.data` (decoders get
`pyarrow.RecordBatch` via the Arrow C Data Interface — `arrow.rs`, the only
`unsafe`); `InstrumentId`, `BarType`; `phasor.validation` (pure NumPy: `rolling`, `expanding`, `purged_kfold` with purge and embargo, `walk_forward` that selects on train and reports the chosen key's test score).

### 12.5 `phasor.Portfolio` and the GIL

- Owns records (sorted once for shared groups), close at source width, column map, groups, scoring, and a `phasor_analysis::Cache` that every method's borrowing Rust `Portfolio` reads and fills (`Portfolio::from_borrowed`), so a value curve derived for one call serves the next; `clear_cache()` releases it.
- Records come back as dicts of NumPy arrays (`orders()`, `trades()`, `logs()`, `reason_counts(col)`).
- **GIL**: factor evaluation, data loading, `from_signals` / `from_orders` and every `Portfolio` derivation release it (`py.detach`); only the NumPy conversions hold it.
- Exposure and excursions are methods too: `allocations()`, `long_exposure()`, `short_exposure()`, `net_exposure()`, `gross_long_short()` return whole `(T, C)` or `(T, groups)` F-ordered matrices, since they are not cached and one column per call would recompute the matrix per column; `position_coverage()` is one value per column. A portfolio keeps only closes, so `excursions(high, low)` and `edge_ratio(high, low)` take the range per call (closes alone when omitted, which can only understate it).
- Research functions sit beside the portfolio, not on it (`src/research.rs`): `phasor.events` (forward paths), `phasor.robust` (PSR, DSR, PBO), `phasor.labels`, `phasor.signals` (seeded random signals) and `phasor.synthetic`. One engine call each; a 1-D input comes back 1-D. Labels and forward paths read the future and must not feed a simulation.
- Not exposed: rolling metrics, drawdown records, indicators, phasor-signals cleaning and ranges, `CallSeq::Explicit`, Polars.

## 13. Research layer: research/phasor_lab

![Pre-registered protocol: an LLM proposes, a human reviews, a contract check approves, then one in-sample run, at most three out-of-sample batches 90 days apart, and forward shadow tracking; every step appends to a hash-chained ledger; the LLM never sees results](img/en/research.svg)

A separate package (`phasor-lab`). The model writes hypotheses and specs; a fixed
protocol decides. The model never sees results, so it cannot fit the data; a
healthy pipeline mostly rejects.

### 13.1 Components

| Component | Detail |
|---|---|
| Ledger (`protocol/ledger.py`) | append-only `ledger.jsonl` in its own git repo, SHA-256 chained, each append committed; counts N and OOS batches |
| Policy (`policy.py`) | periods, data (Binance 1h BTC/ETH/SOL/BNB), costs (fees 0.001, slippage 0.0005), gate, OOS budget (3 batches, 90 days apart), forward rules; versioned by hash |
| Pipeline version (`versions.py`) | hash of policy + judging code; judging changes mark results stale, prompt changes do not |
| Cards and specs | mechanism, horizon, fixed direction; dates and named events rejected; spec parser mirrors `parse.rs:validate` (tested) |

### 13.2 Workflow

`propose` (titles of past tries only) → `review` → `approve` (contract check:
compiles, not NaN-dominated, **prefix-consistent** = no look-ahead, smoke run) →
`run` (once in-sample; failures count toward N) → `oos` → `forward` (retire at
z < −2) → `report`. `calibrate` runs negative controls, including a deliberate
future leak that must be rejected.

### 13.3 The harness and its use of phasor

`types/factor_ts/harness.py`: `FactorSet.compile`, reject `uses_future`, quantized
target weights decided at `t`, executed at `t + 1`, then **one**
`phasor.from_orders(..., size_type="targetpercent", cash_sharing=True, call_seq="auto", column_map=…, threads=4)`
over every member × cost multiplier (0×, 1×, 2×). Gate: t-stat above the
Bonferroni bound `Φ⁻¹(1 − α/2N)`, t ≤ 8 (else suspected look-ahead), positive
Sharpe at 2× costs, consistency across members and assets.
