# Factor expressions

`barq-expr` compiles Qlib-style expressions and evaluates them over the same
column-major `(time × symbol)` panels used by the simulator:

```rust
let factors = FactorSet::compile([
    ("trend", "$close / Mean($close, 20) - 1"),
])?;
let values = factors.evaluate(&FactorInputs::from_ohlcv(&panel)?)?;
let trend = values.get("trend").unwrap();
```

`alpha158()` and `alpha360()` return Qlib's default named feature libraries.
Both need `open`, `high`, `low`, `close`, `volume`, and an explicit `vwap`
field:

```rust
let inputs = FactorInputs::from_ohlcv(&panel)?.with_field("vwap", &vwap)?;
let values = alpha158()?.evaluate(&inputs)?;
let history = alpha360()?.evaluate(&inputs)?;
```

Alpha360 contains 60 normalized observations for each of close, open, high,
low, VWAP, and volume. It returns the raw Qlib features; `DataHandlerLP`
normalization, missing-value filling, and labels are outside this layer.

## Where factors fit

```text
OHLCV ──▶ expressions ──▶ factor Matrix ──▶ delayed/cleaned signals
                                                  │
                                                  ▼
                                      Portfolio::from_signals
```

The expression layer computes information; the strategy decides how that
information becomes an order. In particular, a factor calculated from bar
`t`'s close must be delayed before a strategy fills it on a later bar. See
`crates/barq/tests/factor_path.rs` for the executable path.

The same factor matrices can be exported to a model-training process. Model
training is not part of this crate: its output is just another score matrix
that a strategy turns into signals and feeds to the same portfolio layer.

## Execution backends

Expressions are parsed into a small AST. Evaluation is per symbol, and shared
AST nodes are cached across a factor set, so repeated expressions such as
`Ref($close, 1)` are computed once. Results stay in `Matrix`; this reuses the
existing rolling kernels and avoids a dataframe-to-simulator conversion.

`evaluate()` uses the built-in matrix backend. Enable the optional `polars`
feature to select Polars Lazy explicitly:

```rust
let native = factors.evaluate_with(&inputs, &NativeBackend)?;
let polars = factors.evaluate_with(&inputs, &PolarsBackend)?;
```

Both backends consume the same compiled `Expression` tree and return the same
`FactorValues` shape. `ComputeBackend` is the extension point for another
executor. Backend choice is explicit; there is no data-dependent automatic
selection.

Standard arithmetic and rolling expressions compile to native Polars
expressions. Qlib-specific rolling operations such as last-value window rank
and rolling regression use Polars rolling UDFs so their semantics remain the
same as the native backend.

The reproducible backend benchmark is:

```bash
cargo bench -p barq-expr --features polars --bench backends
```

On the current development machine, using a `1024 × 16` panel and release LTO:

| Workload | Native | Polars | Faster backend |
|---|---:|---:|---:|
| Four element-wise factors | 140.3 µs | 725.6 µs | Native 5.2× |
| Six standard rolling factors | 4.13 ms | 1.04 ms | Polars 4.0× |
| Alpha158 | 139.8 ms | 89.3 ms | Polars 1.6× |

These figures include input/output conversion through the public backend API.
They are a local baseline, not a backend-selection guarantee: expression mix,
panel shape, CPU, and Polars version can change the result.

The supported surface includes Alpha158, Alpha360, and common
single-instrument Qlib operators: arithmetic, comparisons, boolean conditions,
`If`, references, fixed and expanding windows, regression,
correlation/covariance, ranks, moments, WMA, and EMA. `Ref` is row-based,
including on irregular calendars; negative offsets are allowed for labels and
reported by `uses_future()`.

## Compatibility boundaries

- `Rank(x, n)` is the percentile rank of the newest value inside its trailing
  window. It is not a cross-sectional rank.
- `Greater` and `Less` are element-wise maximum and minimum.
- Windows use Qlib's partial-window behavior (`min_periods=1`), and `0` means
  expanding history.
- Missing fields and mismatched panel shapes are errors. Missing observations
  inside correctly shaped fields remain `NaN`.
- Cross-instrument references, masks, and time resampling are outside the
  single-instrument expression scope.

Committed numeric fixtures generated by Qlib pin all 158 and 360 expressions
for both Native and Polars, including irregular dates and missing observations.
Regeneration instructions are in `tests/parity/README.md`; normal Rust tests do
not need Python or Qlib. Unit tests also pin parsing, shapes, special rolling
behavior, and the full factor-to-portfolio composition.
