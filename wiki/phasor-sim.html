phasor-sim

两条按根推进的模拟循环。订单循环每个格子一笔请求。信号循环把信号和止损收成至多一笔，再交给同一个 execute_validated。 组内共享一份现金、按顺序成交；组与组互不影响，并行就切在组上。 成交、滑点和规模级联在执行内核里，这一页只写循环怎样把一根 K 线收成那一次调用。

6模块。四个公开；cash 与 random 是私有模块
4个上游 crate，src 里都有引用
8个入口：两条循环，各自普通 / 日志，串行 / 并行

六个模块做什么

from_orders

每个格子一笔订单。一根 K 线先整组解析价格，再按 CallSeq 调用 execute_validated。列参数不变时，每列的 ValidatedOrder 只构造一次：九次读取和内核十四项检查里的七项被提到循环外。源码里的测量是稀疏 +8% 构造、+20% 校验，合计 +30%；稠密 +11% 与 +10%，合计 +22%。预分配相对按倍增长，在成交密集的扫描上 +19%，在单列长序列上 +6%。

from_signals

每列准备两份 ValidatedOrder：普通滑点，以及止损限价用的零滑点。规模和规模类型沿列不变时，bar 0 之前用全假信号调用一次 signals_to_size，非法规模只报一次，安静的根就可以直接跳过。填充上界是置位信号格的两倍，再封顶到行列数。注释引用订单循环在稀疏负载上测得的 +30%，以及预分配的 +6% 到 +19%。

groups

分组存的是长度，默认 ungrouped：每列长度 1，各有各的现金。长度里出现 0，或总和不等于列数，from_lens 返回 Invariant。is_shared 在任一长度大于 1 时为真，模拟据此才做组一级的净值。chunks 按列数把组切成连续段，合并时按顺序拼接。注释里的例子：5 个组、4 个线程，按组数向上取整会让一个线程空闲。

signals

七步里的纯函数，顺序固定，可以一个一个对照。止损覆盖输入；然后同向的入场和出场；然后多空入场；然后对着持仓的入场；最后 signals_to_size。先解方向冲突再解同向冲突，活下来的信号会不一样。负的 size 直接 Invariant，方向只写在信号上。反手是一笔订单。百分数不能反手。

cash

成交之外的现金。开盘先存款再付股息，收盘再记 earnings。负数流出封顶在 max(free_cash, 0)，记录里是实际入账的数。现金 100、自由现金 40 时，请求取出 50，入账 −40，现金变成 60、自由现金变成 0；再取 1，入账 0。无穷金额是 Invariant。标量 0 或 NaN 整段跳过，按列存放的全 0 仍会逐根读。

random

uniform(seed, row, col) 用 SplitMix64 混合这三项，取高 53 位除以 2^53，落在 [0, 1)。inline(never)，只在 reject_prob > 0 时调用。内核自己不抽样。抽样若改成循环里往前推进的生成器，结果就会跟着分组和线程数变。

模拟流程

三张图按源码顺序画。第一张是两条循环共用的一根 K 线。第二张是信号循环在调用内核之前做的准备。第三张是分组、组内顺序和线程。 买卖公式、规模级联和拒单状态在 phasor-exec。

订单循环 信号循环 分组 现金 Err
1. 一根 K 线。开盘现金，整组解析价格，按序成交，收盘收益。组内净值沿用

订单循环在一列一组时，执行到该列才用「现金 + 这一列的持仓 × 估值」重算净值。信号循环先把组内持仓加总；组长度是 1 时两种加总是同一件事。 成交之后 last_val_price 无条件写成新估值价：它要么是原来的值，要么是有限的成交价。

日志有 38 个字段，订单记录有 7 个。到达内核的订单才写一行，成交与否都写；信号没收成订单的根没有日志。没有成交时 order_id 是 −1。 串行路径上各组共用一个 fills 计数，这样日志能对上同一份缓冲里的成交。

2. from_signals 的 prepare_order。止损先于冲突，冲突只在有入场时发生，然后才定规模

向下的止损水平是锚点 × (1 − 距离)。开盘已经穿过水平，成交价是开盘；水平落在最低和最高之间，成交价是水平。距离小于 0 是 Invariant。 跟踪发生在测试之后，所以这一根用的是上一根留下的峰值。 Close 和 Reverse 会把累积关掉，减仓变体保留累积。减仓本身不重新锚定止损。

3. 组是并行单位。组内一根 K 线上顺序执行。线程各写各的缓冲，再按组顺序接起来

两列共享现金，左列买入、右列卖出。Auto 把近似价值为负的卖出排在前面，买入才能用上刚刚释放的现金。买如果排在前面，会因为现金不够被安静地拒绝。 信号循环里没有待执行订单的列，近似价值记 0。订单循环对每一列都估算，估不出的是 NaN，排到最后。

预分配也写在并行路径的注释里：四个核上，缓冲按倍增长时加速是 1.46 倍，预分配到填充上界后是 1.70 倍。差别来自各线程同时进分配器。 测量数字在 docs/ARCHITECTURE.md §11.2，这里不另写一份。

谁依赖它，用来做什么

crate用到的模块用来做什么

输入长什么样：1m × 5 年 × 3 个标的

sim 只吃 (n_rows, n_cols) 的矩阵和标量/向量参数，不认识“均线”。K 线对齐、复权、asof 关联都发生在进入 sim 之前的数据层 （BarPanel，见 crates/phasor-py/python/phasor/data.py）。策略参数（快/慢均线窗口）是 Python 策略函数的参数，引擎只收到算好后的布尔矩阵。

市场数据与信号

OHLC 都是 (T, 3) 的 float64 矩阵，Fortran（列主序）布局，numpy 缓冲零拷贝借用。 用止损时 high/low 必须给。entries/exits 是 (T, 3) 的 bool 矩阵，通常极稀疏。

交易参数：FlexArray 四种形态

标量（fees=0.001，全部格子共用，不访问内存）、每列一个（init_cash）、每 bar 一个（长度 T）、完整 (T,3) 矩阵。 get(row,col) 是一次内联 match，见 phasor-core。

三个独立账户跑双均线

BTC / ETH / SOL 各 10,000 元独立现金，允许做空。不传 cash_sharing 时是三个长度 1 的 group， shared=false，跳过组价值计算和 CallSeq；threads=3 时三个 group 并行，时间轴各自串行。 

@strategy
def dual_ma(data, fast=10, slow=30):
    f = data["close"].rolling(fast).mean()
    s = data["close"].rolling(slow).mean()
    return crossed_above(f, s), crossed_above(s, f)

pf = dual_ma.run(
    panel,                  # OHLC (T,3)，列 = BTC, ETH, SOL
    direction="both",       # entries→做多入场；exits 在 Both 下是“做空入场”
    init_cash=10_000,       # 每个账户各一份
    size=np.inf,            # 满仓：具体股数由 exec 内核按该账户现金算
    fees=0.001,
    threads=3,

常见问题

Q1. 同一根 bar 同时出现入场和出场会怎样？

系统按配置的冲突模式处理，不替你猜。解析顺序固定：先同方向冲突，再多空入场冲突，最后反向持仓入场。空仓时 Adjacent/Opposite 两个信号都丢弃——没有持仓就没有相邻/相反可言。

配置字段冲突对取值
upon_long_conflict / upon_short_conflict同向 entry + exitEntry / Exit / Adjacent / Opposite / Ignore（默认，两个都丢）
upon_dir_conflictlong_entry + short_entryLong / Short / Adjacent / Opposite / Ignore
upon_opposite_entry入场方向与持仓相反Ignore / Close（只平仓）/ CloseReduce / Reverse（反手，一笔订单）/ ReverseReduce（默认）

对应纯函数在 src/signals.rs：resolve_signal_conflict、resolve_dir_conflict、resolve_opposite_entry。持多 7、exit、accumulate 关闭时出场是全平 7，请求的 size 3 被忽略（见该文件单测 an_exit_without_accumulation_closes_the_whole_position）。

Q2. 止损是用户配置的，还是系统写死的？

止损位和锚定方式全部由输入参数指定，引擎只提供触发规则。默认 sl_stop/tp_stop 是 NaN（不止损）。

字段含义
sl_stop / tp_stop止损/止盈距离，比例（0.1=10%）。NaN 禁用；默认 NaN
sl_trail是否跟随曾到达的最好价格移动止损
stop_entry_price开仓锚定价：ValPrice / Price / FillPrice / Close
stop_exit_price触发后成交价：StopMarket / StopLimit（不收滑点）/ Close / Price
upon_stop_exit / upon_stop_update / use_stops触发后平仓或反手 / 加仓时是否重锚 / 总开关（默认开）

写死的只有触发规则 stop_price：止损位 = 锚定价 × (1 ∓ 比例)；开盘穿透按开盘成交，价位在 bar 区间内按止损位成交；同一根 bar 止损先于止盈。

Q3. simulate_group 怎么判断“有没有订单”？判断后调用哪里下单？

“有没有订单” = 止损触发，或信号经过合并、冲突消解后仍存活，且折算出的 size 非零。判定在 prepare_order（from_signals.rs:502），顺序：

1. read_signals：两套约定 OR 合并成四个 bool
2. 止损已武装 → stop_price；触发则 from_stop 替换信号（最高优先级）
3. 四个信号全 false → 安静 bar 返回 None（稀疏策略大多数 bar 的出口）
4. 含 entry → 三个冲突函数依次消解（可能全部改写成 false）
5. signals_to_size：结合持仓、accumulate 折算带符号 size
6. sized.size == 0 → None；否则返回 Pending

存活的订单在 simulate_group 里 set_bar 到预构建的 ValidatedOrder，然后调用 phasor_exec::execute_validated（from_signals.rs:868）做校验和成交计算。 分层是：信号解析和组内调度在 phasor-sim，校验和成交在 phasor-exec，成交结果落到 sink。

Q4. sink 是做什么的？

sink 是循环与输出存储之间的抽象（phasor-records/src/lib.rs:55 的 RecordSink）。循环只在成交时调 push_order(row, col, size, price, fees, side)、有出入金时调 push_cash(...)，不关心写到哪里。

实现用途
OrderRecordsstruct-of-arrays 内存缓冲（col/idx/size/price/fees/side 六个并列 Vec），零转置交给 Arrow；分析层只从这些记录重建账户
JournalOrderRecords + LogRecords，logged 变体

SinkBuffer 还提供 with_capacity（并行时每线程一个 sink）和 merge（按列序拼接；Journal 合并时重定 log 的 order_id）。 id 在 merge 后才赋值，所以并行结果与线程数无关。用 trait 而不用具体数组，事件驱动层将来可复用同一记录格式。

Q5. 给到 sim 的订单是提前向量化算好的吗？

输入数据是向量化矩阵，订单决策在循环内逐 bar、逐列现场生成。决策依赖当前持仓、止损锚定价和 accumulate 状态，时间轴上是硬循环依赖，无法提前批量算。 静态部分被上提：手续费等九个参数和七项静态校验每列只构建一次 ValidatedOrder，每 bar 只 set_bar 四个动态字段（参数声明随行变化时才重建）。 并行轴在空间方向（group/列），时间方向始终串行。

与 vectorbt：结果对齐，算法不同

撮合语义对齐 vectorbt 1.1.0 开源版：同一输入产出相同成交记录和分析结果。实现重新设计，没有复制代码。 保证方式是差分测试，而不是“看起来差不多”。

环节做法
录制tests/parity/generate_*.py 在隔离环境（.venv-parity）运行真实 vectorbt 1.1.0，输出提交为 tests/fixtures/*.tsv
回放cargo test --workspace 每次逐字段比对，无需 Python：撮合内核、信号流水线、止损、现金共享、交易视图、回撤、28 项统计指标
在线对照Python 测试在装了 vectorbt 时实时重算一遍（crates/phasor-py/tests）
钉死的细节min_size 默认 1e-8、跳空按开盘成交、同根 bar 止损先于止盈、反手是一笔订单、Direction::Both 下 exit 是做空入场

为什么快，还能更快吗

先澄清一个前提：把分支密集的标量循环改写成 Rust 本身不带来加速——vectorbt 自己的 Rust 后端比 Numba 慢（0.74–0.82×），Numba 已经发射 LLVM 机器码。差距来自设计。 下面的数字来自 docs/ARCHITECTURE.zh-CN.md §15.1（4 核 Xeon，两个引擎同场测量）。

2.6–3.3×单线程对 vectorbt Numba
9.7–12.1×4 线程对 vectorbt Numba
3.62× / 1.63×稀疏 / 稠密负载的 4 线程扩展（90% / 41%）

最大一块：把 sweep 变得可并行

参考事件驱动引擎状态在全局消息总线后面的 Rc<RefCell>，结构上只能顺序跑。phasor 没有 Rc/RefCell/全局状态， group 是并行单位：std::thread::scope 连续分块、各线程自有状态和 sink、无锁无归约、合并后赋 id，串行与多线程逐位一致。

单线程：循环本身的设计

列主序扫描匹配内存访问；账户状态是栈上紧凑结构，内核单态化内联；FlexArray 标量快路径不访问内存，numpy 零拷贝； 列常量订单只构建一次；安静 bar 早退；缓冲按成交上界预分配；column_map 让参数扫描不复制行情。
