phasor-records

记录层，是向量化层和第二阶段事件驱动层之间的契约。两层的算法完全不同，永远不会共用一个模拟循环， 但它们产出同样的记录。统一的是输出，不是计算，所以分析层只需要写一次，两层的结果也能逐列对照。 这个 crate 定义记录的结构（成交、现金流、日志），并从记录派生交易、回撤和 MAE/MFE，再提供按列分段归约。

从第一性原理看：回测的账本

这一节先不看 phasor 的代码，只回答两个问题：这一层在量化研究里对应什么概念？如果从零开始实现，它的形状应该怎样一步步推出来？ 后面各节再讲 phasor 对每个问题的具体回答。

1. 回测真正产出的是什么

回测引擎本质上是一个模拟的券商。真实交易中，券商给你的东西只有两样：成交回报（哪个标的、什么时候、买卖多少、成交价、手续费）和资金流水（入金、出金、利息、分红）。 持仓、现金余额、净值曲线、每笔交易的盈亏、夏普、最大回撤，没有一样是券商“给”的，全都是你从这两样东西算出来的。 这正是会计里“原始凭证 → 账簿 → 报表”的分层，也是软件里的事件溯源（event sourcing）：状态 = 对事件序列的折叠，事件只追加、不修改。

事件是唯一的事实来源；状态是事件的折叠；视图和统计量都是纯函数

2. 为什么存记录，而不是存状态矩阵

最直接的做法是每根 K 线、每个标的存一份持仓和现金（行 × 列的矩阵）。它能用，但作为“事实”是错误的选择：

稀疏

成交只发生在少数 K 线上，持仓矩阵绝大多数格子是上一格的重复。记录的大小与交易活动成正比，而不是与 行 × 列 成正比；千列参数扫描时，这个差别是几个数量级。

可审计

状态矩阵只说明“现在是多少”，记录说明“为什么是这么多”。每一分钱都应该能追到一条事件，这是对账（reconciliation）的前提，也是回测结果可信的前提。

与引擎无关

向量化引擎和事件驱动引擎的算法完全不同，但只要它们产出同样的事件，分析就只需写一次，两者的结果能逐条对照。统一输出，不统一计算。

路径相关的事实无法重算

含滑点的成交价、部分成交、按当时可用资金封顶的出金，事后都无法从输入复原。由此得到一条硬规则：凡是改变现金或持仓的事，都必须是一条记录，否则从记录重建的账簿就和模拟器对不上。

3. 最小的事件结构是怎么推出来的

一笔成交要回答四个问题：谁（哪个账户/标的列）、何时（哪根 K 线）、多少、什么方向、什么价格、付了多少成本。每个字段怎么表示，都有可以说清的理由：

选择理由反面
时间用 K 线下标，不用时间戳和价格矩阵天然对齐，查任一时刻的价格是 O(1) 的下标访问。时间戳要再做一次对齐/查找，且多资产日历不一致时有歧义。
数量恒为正，方向单独一列“卖出”和“做空”是两个概念：卖出 1 可能是平多也可能是开空。方向显式存储，成交量可以直接求和。带符号的数量让“平仓还是反手”要靠上下文推断。
价格存实际成交价（含滑点），费用单独一列PnL 可以拆成价格贡献和成本贡献，才能做交易成本分析、换费率重估。把费用并进价格后，成本无法再分离出来。
非成交现金流是另一种事件入金、利息、分红改变余额但没有成交，同样需要 谁 / 何时 / 多少 / 类型。金额记实际入账额，而不是请求额。只从成交重建现金，入金和分红会让余额对不上。
记录的身份由确定的顺序决定id 应当是“排好序之后的位置”，而不是“谁先写进来”。用共享计数器分配 id，并行时 id 取决于线程交错，结果不可复现。

4. 从成交到“交易”：配对问题

一笔成交不是一笔交易。要谈论“这笔交易赚了多少”，就必须决定哪笔出场对应哪笔入场。这就是税务和会计里的批次配对（lot matching）问题：先进先出（FIFO）、后进先出（LIFO）、平均成本、指定批次，都是被广泛使用的合法规则。 第一性原理给出一条不变量： 

总 PnL = Σ 卖出金额 − Σ 买入金额 − Σ 费用 + 期末持仓按市价估值

右边只有现金流，没有任何配对信息，所以总 PnL 与配对规则无关。配对改变的只是归因：交易笔数、单笔收益、胜率、期望、持有期。 这意味着“胜率”“期望”这类统计量必须注明它基于哪种配对，否则不同系统之间无法比较。下面同一串成交，四种规则：

成交：买 1@10（t0）、买 1@20（t1）、卖 1@25（t2）、卖 1@15（t3）
规则配对单笔 PnL胜率总 PnL
FIFO10→25，20→15+15, −550%10
LIFO20→25，10→15+5, +5100%10
平均成本均价 15 → 25，15 → 15+10, 050%10
整个仓位空仓 → 空仓一段+10100%10

设计上要定的几件事

提供哪些规则。回测里常见的是平均成本类（按入场或按出场归因）加上“整个仓位”这种不需要配对的视图：从空仓到空仓算一段。

反手怎么处理。多 1 时卖 3：一笔成交跨过了零点，必须拆成“平掉 1”和“新开 2”，费用按数量比例分摊，否则一个仓位里会出现两个方向。

期末未平仓怎么办。用最后的价格标记，并显式标注“未平仓”，让统计可以选择是否纳入。

“全平”怎么判断。浮点数下 0.1 + 0.2 卖出 0.3 不一定恰好归零。必须用容差判断，并把残差吸附到 0，否则会留下“灰尘仓位”和本该为 0 却是 1e-14 的“伪盈利”。

5. 只看终点不够：路径与风险

账户的路径：回撤段

最大回撤只是一个数字。把净值曲线切成一段段 峰 → 谷 → 恢复（或尚未恢复），得到的是一个分布：多深、跌了多久、爬回来用了多久。恢复通常比下跌慢，这才是回撤真正的代价。实现前要先定义边界：平台算不算新峰、恰好回到旧峰算不算恢复、缺失数据能否结束一段回撤。

单笔交易的路径：MAE / MFE

PnL 说明交易停在哪里，最大不利偏移（MAE）和最大有利偏移（MFE）说明它中途走了多远（Sweeney 提出的分析方法）。它需要 OHLC 行情，不只是成交，用来回答止损是不是放在噪声里、出场是不是放走了大部分行情。K 线内部没有路径信息，所以入场那根的高低点要不要计入，必须事先选定一个保守的约定。

6. 统计量：一律是按列分组归约

平均 PnL、每列交易数、最差交易发生在哪一行、收益前五名，本质都是同一个操作：把记录按账户/列分组，每组归约成一个值（split-apply-combine）。 与其为每个指标手写循环，不如实现一个分组内核加一组命名归约。这个内核要事先定死三件事：

空组也要有输出

没有交易的列也必须得到一个值（调用方给的填充值）。丢掉它，结果就和列标签错位，参数扫描的输出变成无法归因的数字。

NaN 的语义逐个定义

count 计不计 NaN？全 NaN 的 sum 是 0 还是 NaN？argmax 遇到 NaN 跳过还是替换？每个归约都要明确，而且要跟你对照的参考实现一致。

顺序与平局确定

组内保持原始顺序（稳定），并列时取第一个还是最后一个要写清楚。否则同一份数据换个输入顺序，结果就变了。

7. 如果从零实现，按这个顺序

  1. 定事件结构。成交和现金流两类，写清每个字段的单位、符号和取值范围。
  2. 定顺序与身份。每个分区（列/组）内按时间追加，分区之间按固定顺序合并，id = 合并后的位置。这样串行和并行逐位相同。
  3. 写入接口与存储分离。模拟循环只调用“记一笔成交 / 记一笔现金流”，具体存什么（只存成交，或成交加诊断日志）由类型参数决定，关掉诊断时零开销。
  4. 列式存储。用结构数组而不是结构体数组：分析时通常只读一两个字段，交给 Arrow/NumPy 也不需要转置。
  5. 派生全部是纯函数。事件 → 交易、净值 → 回撤段、交易 + 行情 → MAE/MFE。不回写事件，不持有隐藏状态。
  6. 统一数值政策。配对中的“全平 / 部分平 / 反手”用容差判断，差值吸附到零。
  7. 一个分组归约内核。覆盖空组、NaN、平局；有序输入走零拷贝快路径，乱序输入走 gather。
  8. 可选的诊断日志。每张被考虑的委托记下请求、前后状态和结果原因，默认关闭，因为它比成交多得多。
  9. 用不变量验证。各种配对的总 PnL 相等；从记录重建的现金等于模拟器内部的现金；“仓位的仓位”等于仓位；最后与独立的参考实现做差分对照。

模块：它依赖什么、被谁使用。上游 crate：它的哪一部分被拿来做什么。下游 crate：它在哪里读写记录。

crate 内部

只有一条主干：几乎每种记录都通过 mapped::ColMap 按列切段。OrderRecords 内嵌 CashRecords，Journal 由成交和日志两半组成。

模块之间的引用。箭头从使用方指向被用的类型

trades 是 mod trades（私有模块），对外只通过 crate 根的 pub use 暴露 TradeRecords、entry_trades、exit_trades、positions。其余六个模块都是 pub mod。

七个模块做什么

lib.rs：成交记录与写入口

OrderRecords 是结构数组：col、idx、size、price、fees、side 六列，加一个内嵌的 cash。id 不存储，就是记录在合并后数组里的位置。RecordSink 是模拟循环写成交和现金流的接口，SinkBuffer 再加上 with_capacity 和 merge，让同一份线程代码同时服务普通运行和带日志的运行。

cash：不是成交的现金流

入金/出金、利息、分红会改变余额，但没有成交。实际入账的金额与路径有关（出金要按当根 K 线的自由现金封顶），事后无法从输入重算，所以必须像成交一样记下来。它放在 OrderRecords.cash 里，所以已有的 sink、合并、排序、构造函数会一并带上它。

trades：成交 → 交易

一笔成交不等于一笔交易。把卖出归到哪些买入上有三种站得住的规则，所以这里三种都提供，结构相同，只是一条记录的含义不同。三者总 PnL 一致，但交易笔数、单笔收益、胜率、期望值都不同。这是整个设计里最常被移植错的部分。

mapped：按列分段归约

平均 PnL、最差交易所在的行、每列交易数、收益前五名，都是同一个操作：把扁平数组按列切段，每段归约成一个值。ColMap 做切分（稳定计数排序），MappedArray 做归约。记录已按列排好时直接切子切片，不需要 gather，也不分配内存。

drawdowns：每段回撤一条记录

最大回撤只是一个数字。这里每段回撤一条记录，带峰值、谷底、结束位置以及是否已恢复，于是一列的回撤历史可以走普通的 mapped 归约。最后一段没回来的回撤标为 Active，它的恢复时长只是一个下界。

excursions：MAE / MFE

PnL 说明一笔交易最后停在哪，excursion 说明它中途走了多远。MFE 是持有期内最好看的时候，MAE 是最难看的时候，都从入场价量起。用来判断止损是不是放在了噪声里、出场是不是留下了大部分行情。edge_ratio 是平均 MFE 除以平均 |MAE|。

logs：一张订单的前后全貌

成交记录只说明发生了什么。日志记下“要求的是什么”，以及订单前后的账户状态，这样才能回答回测让人意外时最常见的问题：这根 K 线为什么没成交？没有日志时，唯一的证据是“没有成交记录”，可能的原因有十几种；有了日志，原因就是一个字段。Journal 把成交和日志放在一起，合并时负责重定位 order_id。

记录从哪来，到哪去

上面一行是生产：模拟循环通过 trait 写记录，每个组（并行时每个线程）各自拥有一个缓冲，结束后按组序合并。 下面一行是消费：分析层先把记录排成列主序，再从中派生交易和回撤，最后按列归约成统计量。

成交记录与排序契约

记录按列主序输出：先是第 0 列的全部成交，然后第 1 列，依此类推。id 就是记录在合并后数组里的下标。 这是并行模拟可复现的原因：每列（每组）往自己的缓冲里写，没有共享计数器，缓冲按列序拼接，id 在拼接之后才分配。 如果用一个共享的原子计数器，id 就会取决于线程的交错顺序。

并行合并：每段拷进互不相交的区间

稠密的并行运行每个线程会产出几百万条成交，在 join 之后的单个线程上把它们全部拷一遍，会占掉明显的一段墙钟时间。 超过 PARALLEL_CONCAT = 1 << 16（65,536）条时，OrderRecords::concat 先分配清零的输出（页面是惰性分配的，第一次触碰的线程就是拷贝它的线程）， 再用 split_at_mut 把每一列切成每段一个不相交的区间，在 std::thread::scope 里并行拷贝。现金流每根 K 线最多几条，串行拷一遍就够了。

四段缓冲 → 一个输出。每个区间只有一个写者，所以不需要锁，结果与串行 extend 逐位相同

三种交易视图

同一串成交，三种归因规则。entry_trades：一条记录代表一笔入场成交，整个仓位的出场按数量加权平均后分摊给每笔入场。 exit_trades：一条记录代表一笔出场成交，用自己的价格，入场被平均进来。 positions：一条记录代表一个仓位，由前两者之一按 parent_id 聚合而成。 下面的计算器把 Rust 的三个函数逐行移植成了 JavaScript：改一下成交，看看笔数和胜率怎么变，总 PnL 怎么保持不变。

单列成交。每行一笔：行号 方向(B/S) 数量 价格 [手续费]，行号必须递增

PnL = (出场价值 − 入场价值，空头取反) − 入场手续费 − 出场手续费；ret = PnL / 入场价值。差值用 add 而不是 -，所以同价往返恰好是 0。 持有长度：已平仓按开区间 exit − entry，未平仓按闭区间 exit − entry + 1。已平仓的出场那根 K 线属于下一段，未平仓的最后一根它仍然持有。 “胜率”这里只是 pnl > 0 的比例，用来演示三种视图的分歧，不是分析层的统计定义。

部分平仓：两边的处理不同

exit_trades 把剩余仓位的入场数量、金额、手续费按比例缩小，不是从前往后消耗，所以剩下部分的平均入场价不变。entry_trades 在部分平仓时什么都不输出，仓位结束时整体标为 Open，每笔入场都以“已出场部分 + 收盘价标记的剩余部分”的加权价出场。

反手：一笔成交被拆成两半

多 1 时卖 3：平掉多头的那 1 属于旧仓位，剩下的 2 开出新的空头仓位，手续费按数量比例分给两边。parent_id 加一。positions 因此永远不会在一个仓位里看到两个方向。

单笔仓位原样拷贝

仓位只含一笔交易时，positions 用 push_copy 原样复制，不重新推导。重新推导会算 size × price / size：5.128 × 58.78 / 5.128 = 58.779999999999994，PnL 末位跟着变。拷贝保证仓位与它唯一的交易逐位相同，positions(positions(x)) == positions(x)。

回撤记录

四个下标里只有三个是显然的。peak_idx 是下跌之前的最后一根 K 线，start_idx 是下跌的第一根，恒等于 peak_idx + 1，但仍然单独存储，因为两者度量的东西不同。 等于峰值算上涨：顶部的平台会延长峰值而不是开出新回撤；已经在水下时，恰好回到旧峰值就算恢复。结束一段回撤的那根 K 线就是下一段的峰值，所以 V 形反弹后紧接着再跌会产生两条记录。

输入一列序列（逗号分隔，nan 表示缺失）。阴影是一段回撤，从 start 到 end

duration：已恢复按开区间 end − start，仍在水下按闭区间 end − start + 1，与交易持有长度同一条规则。 decline_duration = valley − start + 1（从 start 而不是 peak 量，顶部那根平的不算下跌）； recovery_duration = end − valley（谷底那根属于下跌）。缺失的 K 线什么都不推进，也不能结束一段回撤：数据里的缺口不是策略的证据。

最后一根是 nan 时，还在水下的那一段不会被标成 Active，而是不产生记录：判断“最后一根”的代码在 continue 之后。这与 vectorbt 一致， parity_drawdowns.rs 专门枚举了带尾部缺口的路径，单元测试 a_missing_bar_is_not_evidence_about_the_strategy 也把它钉住了。选上面的“尾部缺口”预设可以看到。

MAE / MFE

MAE（Maximum Adverse Excursion，最大不利偏移）是持有期间价格朝亏损方向走得最远的距离，即这笔交易最难看的时候浮亏有多深； MFE（Maximum Favorable Excursion，最大有利偏移）是持有期间价格朝盈利方向走得最远的距离，即最好看的时候浮盈有多高。两者都从入场价量起。 这套分析方法由 John Sweeney 在 1990 年代提出。

例子（与下图相同）：做多，入场 100，持有期最低 97、最高 108，出场 104
计算含义
PnL104 − 100 = +4最后赚了 4
MFE108 − 100 = +8中途最多浮盈 8
MAE97 − 100 = −3中途最多浮亏 3

做空时反过来：MFE = 入场价 − 最低价，MAE = 入场价 − 最高价。

为什么要看它们

PnL 只说明交易最后停在哪，MAE/MFE 说明它中途走过哪。

止损放得对不对：把所有交易的 MAE 画出来，如果盈利交易的 MAE 普遍到过 −3，而止损设在 −2，止损就放在了正常波动里，会把本来能赚的交易提前砍掉。

出场早了还是晚了：上例 MFE 是 8、最后只拿到 4，一半利润还了回去；大部分交易都这样，说明出场规则有改进空间。

edge ratio = 平均 MFE / 平均 |MAE|。大于 1 表示入场后价格平均朝有利方向走得比不利方向远，入场本身有优势。

phasor 的约定

按单位数量计，是价格距离而不是金额；*_ret 再除以入场价。MFE 永远 ≥ 0，MAE 永远 ≤ 0，多空都一样：两个极值都用入场价做初值，从未朝有利方向走过的交易 MFE 正好是 0。 窗口是入场那根到出场那根，两端都包含；未平仓交易按状态延伸到 n_rows − 1，不看记录里写的 exit。某根的 high 或 low 缺失时用该根 close 代替。

入场那根 K 线的整个区间都算进去，尽管成交可能发生在收盘，高低点早已出现过

没有 K 线内部的路径能区分两种情况，所以这里宁可报大一点的 excursion。对 MAE 这是保守的一侧，而止损位置看的正是 MAE。出场那根同理。

分段归约：ColMap 与 MappedArray

ColMap::build 对记录下标按列做稳定计数排序，记录以什么顺序到达都能用，这也是参考实现一直的做法。 但本引擎按构造输出列主序记录，此时一列就是一段连续切片，没有什么需要 gather。build 会顺手检测这一点， for_each_column 随后直接给出子切片，不分配内存。gather 路径仍然存在且正确，因为来自合并、过滤或第二阶段事件驱动层的记录不一定有序。

空列也是一列

每个归约对每一列都返回一个值，包括没有任何记录的列：它们拿到调用方给的 fill，归约函数不会在空切片上被调用。丢掉它们会让结果和列标签错位，扫描输出就变成了无法归因的数字。

方法空列NaN 的处理备注
count()0计入唯一计入 NaN 的归约。与其它归约配对，说明那个统计量实际基于多少条记录。
sum()0跳过；全 NaN 的列和为 0没有值的和是 0，与 nansum 一致。用 count 区分“全缺失”和“真的持平”。
mean()NaN跳过；全 NaN 为 NaN
min() / max()NaN跳过fold(NaN, f64::min)。
std(ddof)NaN跳过；有效数 ≤ ddof 为 NaN按参考实现的写法：先求总体方差再缩放，((ss / n) * n / (n − ddof)).sqrt()，与 ss / (n − ddof) 末位不同。
idxmax / idxminfill替换成 −inf / +inf，不是跳过并列取第一个。只有在一列同时有 NaN 和“输的那一侧”的真无穷时才和“跳过”不同。全 NaN 返回 None → fill，参考实现会抛异常。
top_n_mask / bottom_n_mask—NaN 最后被选，从打破并列的那一端补齐top 从列尾开始打破并列（后出现的赢），bottom 从列首开始。这种不对称来自参考实现。
stack_expand(fill)整列 fill原样max_col_len × n_cols 的矩阵，顶部对齐。第 i 行是该列第 i 条记录，不是K 线下标。
value_counts(codes, k)全 0—k × n_cols，第 k 行统计代码为 k 的记录，用来汇总方向、状态这类分类字段。

日志：为什么这根没成交

日志对每张被考虑的订单写一行，而不是每笔成交：稀疏策略上行数是成交的二十倍，宽度是五倍，千列扫描就是几个 GB 没人看的数据。 所以它按订单开关，通过请求自己的 log 标志，而且像其它参数一样是 FlexArray。有用的形态只有三种：处处关闭（默认）、只开要排查的那一列、在一次扫描中只开某一行。
