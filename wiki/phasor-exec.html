phasor-exec

订单执行内核。向量化循环现在调用它，阶段 2 的事件驱动也会调用同一个 execute_order。 一次调用只看见一个账户、一笔订单、一根 K 线，不读取这一列的其他行。 成交要和参考实现逐字段一致，所以这里的分支顺序、取整和加法都照着那个顺序写。

2模块：types 放状态和订单，kernel 执行一笔。买卖函数不公开
3个 crate 在 src 里使用。phasor-sim 调用内核，另外两个拿类型
1笔订单进，一份账户状态加一份 OrderResult 出。纯函数，抽样由参数传入

点一个节点

模块说明它被谁使用；上游说明 kernel 或 types 拿它做什么；crate 说明它拿 phasor-exec 的哪一部分。

crate 内部

types 不引用 kernel。kernel 读取 Order 和 ProcessOrderState，返回 ExecuteOrderState 与 OrderResult。下面六个函数都是 kernel 私有的。

kernel 使用 types。执行步骤留在 kernel 里面

模拟循环调用 execute_validated，并持有 ValidatedOrder。raise_reject 和 log 写在 Order 上，kernel 的分支不读它们。

两个模块做什么

types

ExecuteOrderState 是一笔订单能改写的四项：现金、带符号持仓、空头债务、自由现金。债务按开空时的均价记卖出所得。开空或加空时，自由现金的变动是所得减去两倍空头市值：一份是持仓自己的价值，一份是往返保证金。平空按 debt / |position| 对称释放。只留现金和持仓、再把这两项推导出来，做不到，因为保证金和路径有关。ProcessOrderState 在这四项之外加上估值价、组合净值、下一条订单记录和下一条日志的下标。Order 的默认值把无穷和 NaN 当作活的哨兵。

kernel

execute_order 就是 execute_validated 加上当场构造的 ValidatedOrder。两者的成交、拒单和报错位置一致。后者存在，是为了让一列共用的七项参数检查提到循环外。ValidatedOrder::new 记下违规句子，不在构造时失败：参考实现先忽略 NaN 数量，再做校验，所以一整列 NaN 数量配上非法费率，仍然要返回 Ignored。set_bar 改数量、价格、规模类型和方向，这四项不在那七项检查里。

执行流程

下面三张图按 kernel.rs 里 execute_validated 的顺序画。 侧框是这条路径的返回。主列继续向下。 颜色：蓝是还在函数里，黄是 Ignored，橙是 Rejected，红是 Err，绿是成交方向。

继续 Ignored Rejected Err 成交
1. execute_validated 的主链。归零之后，忽略先于校验，本根校验先于列参数

内核测试：现金 100，费率无穷，数量为 NaN，返回 Ignored · SizeNaN。同一笔订单把现金改成 −1、数量改成 5，错误文本里是 cash，因为本根检查先跑。 reject_prob = 0.5 时，抽样 0.1 得到 RandomEvent，现金仍是 100；抽样 0.9 成交，现金变成 50。不传抽样则是 Err。

Order 默认 price = +∞，注释里的意思是用这根 K 线的收盘价。这个替换由调用方在进入内核之前做完。内核在 PriceNaN 之后要求价格有限且大于 0，+∞ 会在 validate_bar 里成为 Invariant。 phasor-sim 在 execute_validated 返回之后才读 raise_reject：状态是 Rejected 且该字段为真时，模拟循环再返回 Err。log 决定模拟循环写不写日志。

2. 规模级联。每一级改写 size_type，走到买卖时只剩 Amount，或 Percent 留下的带符号无穷

按这个顺序代入。方向 Both，value = 1000，val_price = 10，持仓 20，请求 TargetPercent 0.5：乘净值得 500（TargetValue），除估值价得 50（TargetAmount），减持仓得 30（Amount），30 大于 0，进入 buy。ShortOnly、Amount 4：先变成 −4，进入 sell(4)。Both、Amount 为负无穷：改成 Percent −1，percent = 1，数量变成负无穷，进入 sell。

sign 与 numpy 一致：正数 1，负数 −1，0 和 NaN 都是 0。val_price 先看无穷和非正，那是 Err；NaN 排在后面，是 Ignored。Value 与 TargetValue 共用这一级，出去的类型不同。

3. buy 与 sell。数量在进入时都是正的。percent 为 NaN 表示没有百分比上限

买的上限先处理 lock_cash，再与 cash、order.cash_limit 取小，然后才乘 percent。cash_limit 为 100、Percent 0.5 时，最多花 50。 平空且 lock_cash：回补后仍有余款，上限是 free_cash + 2×debt；不够回补，先解出能回补的数量，上限是买下这一段所需的现金，费用含在内；刚好够，上限是 cash。 付得起用 is_close_or_less。付不起时费用在上限里面：源码注释写，费率 10%、固定费 1、现金 100，可买名义是 90。付不起固定费则 CantCoverFees。

卖出在 lock_cash，或数量为无穷且带 percent 时，用自由现金加上平多所得计算可卖上限。总自由现金小于等于 0 且已无多头：NoCashShort。有多头但没有余款做空：只平多。上限小于等于 0：CantCoverFees。 percent 在 lock_cash 分支里乘完后写成 NaN。到手现金为负也是 CantCoverFees。 新债务只覆盖结果里新空出来的那一段。已是空头时，这一段就是本次卖出数量；从多头穿过零时，这一段是新持仓的绝对值。 buy 和 sell 里决定分支的与 0 比较是精确相等。换成 is_close 会改变哪些订单成交。

fees, fixed_fees0都必须有限。买的时候含在现金上限里。
slippage0有限且大于等于 0。买是乘 (1+滑点)，卖是乘 (1−滑点)。

reject_prob0有限且在 [0, 1]。大于 0 时必须传入抽样。抽样小于它则 Rejected · RandomEvent。
lock_cashfalse为真时，买入用自由现金和空头保证金解上限；卖出用自由现金加平多所得解可卖量，并在那一步消耗 percent。
allow_partialtrue为假时，有限请求被 max_size 或现金缩小，返回 Rejected · PartialFill。无穷请求不会被当成部分成交。
raise_rejectfalse留在订单上。phasor-sim 在内核返回后，若结果是 Rejected 且此字段为真，再变成 Err。
logfalse留在订单上。模拟循环用它决定是否写日志。kernel 不分支。

不能绕开的规则

金融比较走 phasor-core 的 math。这里三套数值政策同时存在：贴近 0 用 is_close，买得起用 is_close_or_less，买卖函数里决定走哪条分支的与 0 比较是精确相等。余额大多用 add。卖出有三处普通加法：new_cash、new_debt，以及结果不再是空头时的 free_cash。 容差边界的夹具存在，是因为曾经把 is_close_or_less 换成 <= 时单次对照仍然全部通过。序列夹具把内核自己的输出喂给下一步，用来看见归零没做干净时才会积累出来的残差。 
Ignored / Rejected 是 OrderResult     // 状态停在归零之后。Err 只留给不变量
SizeNaN、PriceNaN 在 validate_bar 之前
validate_bar 然后 param 检查           // 两边都坏时，报本根那句
draw < reject_prob                     // 在 buy / sell 之前
order_size > 0 → buy，其余 → sell      // 0 和 NaN 走 sell
买的 SizeZero 比较 adj_size            // 反解之后的 final_size 不参与这一关
数量与现金上限都无穷 → Err             // 无限做多，在 buy 内
可卖量无穷 → Err                       // 无限做空，在 sell 内
buy: new_cash = add(cash, −花费)
sell: new_cash = cash + 到手

谁依赖它，用来做什么

crate用到的模块用来做什么

phasor 的 prelude 再导出 ExecuteOrderState、Order、OrderResult、ProcessOrderState。phasor::exec 暴露整个 crate，包括 ValidatedOrder 和两个执行函数。prelude 本身不导出那三个名字。
