phasor-model

领域模型。phasor-core 回答“数怎么存、怎么比”，这个 crate 回答“这些数是什么”：一笔订单可以怎样描述、一次撮合可能有哪些结果、 一个标的叫什么、一根 K 线长什么样、钱用什么类型存。它没有任何算法，只有类型；但这些类型的判别值被写进记录数组，是磁盘格式的一部分。

17 个 repr(i8) 枚举判别值由测试固定：它们以整数写进订单记录和日志，被 Python 层和差分测试读回
8 个 crate 直接依赖exec、sim、records、analysis、data、expr、py 和门面 phasor；向量化热路径只用到枚举和 OhlcvPanel
两条血统撮合枚举跟随 vectorbt（逐笔对齐是验收标准）；数值与标识类型跟随 NautilusTrader（阶段 2 的策略 API）

从第一性原理看：领域模型该放什么

先不看代码。一个回测引擎要和别人对账（参考实现、Python、磁盘上的记录），哪些概念必须有唯一、稳定的定义？

1. 订单的“语法”必须是有限集合

“买多少”可以是单位数、金额、可用现金的百分比，或者是目标仓位；同一根 K 线上进场和出场同时触发怎么办；止损按哪个价格挂、触发后按哪个价格成交…… 这些都不是数值，而是选项。把它们写成字符串，每根 K 线每一列都要比较一次字符串；写成布尔组合，非法组合无处不在。正确的形状是枚举， 而且因为结果要写进数组、跨语言读回，枚举必须有固定的整数判别值。

2. “没成交”要说清楚为什么

一次扫描跑了 5,000 列，其中 300 列一笔都没交易——用户第一个问题就是“为什么”。所以结果不能只有“成交 / 没成交”，还要有原因码： 价格是 NaN、钱不够、数量低于最小值、手续费都付不起……每一种原因单独一个值，才能按原因统计。

3. 钱和标识的类型，要为“事件驱动”预留

向量化层为了速度全用 f64，靠 phasor-core 的容差层兜住误差。但事件驱动层（逐笔撮合、真实交易所接口）需要定点数： 百万笔成交在浮点里累加的漂移，和 alpha 是同一个量级。标的名在每次写记录时都会被比较，最好是可以按整数比较的句柄。 这一层现在可以先定形状，让阶段 2 换实现时不动调用方。

4. 行情有两种形状

事件驱动的策略一次看一根 K 线：需要一个 Bar 结构体（数组结构里的“一行”）。向量化引擎一次扫完一列：需要结构体数组， open、high、low、close 各自一块列主序缓冲区。两种形状都要有，而且不能互相冒充。

两条血统，以及阶段 1 里哪些类型真正被用到。实线框：阶段 1 的向量化路径在用；虚线框：为阶段 2 预留，工作区里还没有使用者

每一行都是独立实现，按公开语义编写，没有从任何一个项目里拷贝代码（ARCHITECTURE 附录 A）。BarType 的字符串格式和 SYMBOL.VENUE 都是 Nautilus 的约定。

如果从零实现，按这个顺序

  1. 先列出撮合的全部选项，写成固定判别值的枚举。#[repr(i8)] + 显式 = n，再写一个测试断言判别值——改一个数就是改磁盘格式。
  2. 结果与原因分开。OrderStatus 只有三种（成交 / 忽略 / 拒绝），原因另放在 StatusInfo；记录里存整数，再提供“整数 → 枚举 → 文字”的回路。
  3. 标识：先定类型，再优化。调用方只看到不透明的 InstrumentId，内部先用 Arc<str>，等有性能数据再换成驻留句柄。
  4. 行情：两种形状都给。向量化层用结构体数组 OhlcvPanel，事件驱动层用 Bar；K 线带两个时间戳，回放只按“可用时间”排序。
  5. 钱：定点数，哨兵值代替 Option。原始整数 + 精度；用 i64::MAX 表示“没有价格”，省掉内循环里的判别分支，代价是构造函数要负责把关。

SizeType 是一条级联

phasor-exec 按固定顺序把 Percent、TargetPercent、TargetValue、Value、TargetAmount 逐级改写，直到只剩 Amount（ARCHITECTURE §7.3）。枚举本身只定义“数量怎么读”，换算在内核里。

Rejected 不是 Err

OrderStatus::Rejected 是返回值里的普通结果，原因在 StatusInfo。Err 留给 phasor-core 的不变量错误。

三种交易视图共用一个 schema

TradesType 的三个值只改变成交如何归属到交易：按进场 FIFO、按出场平均、或按仓位聚合。这是移植时最常见的错误（§9.5）。

拒单原因：从记录里的整数读回来

日志记录里 res_status_info 是一列 i64：成交的订单没什么要解释，写 -1；被忽略或被拒的订单写原因的判别值。 StatusInfo::from_discriminant 是回路，describe 给出人话。粘一列整数进来试试，再看按原因统计。

标识：InstrumentId 与 BarType 的解析

InstrumentId 渲染为 SYMBOL.VENUE，用 rsplit_once('.') 解析——从右边切，所以 BRK.B.NYSE 的标的是 BRK.B。 BarType 是 SYMBOL.VENUE-STEP-AGGREGATION-PRICE-SOURCE，用 rsplitn(5, '-') 解析——同样从右边切，标的名里可以有 -（BTC-USDT）。 两者都是 phasor-data catalog 的目录名（<root>/data/<name>/<key>/），所以解析时拒绝空白、控制字符和路径分隔符。

文档与实现的差距：ids.rs 的模块注释说“驻留把每个标识压成一个 Copy 句柄，按整数比较”。现在的实现不是这样： Symbol、Venue 是 Arc<str> 的包装，InstrumentId 只是 Clone，相等比较按字符串内容。 注释自己也说明了“阶段 1 保持简单，有性能数据之后再优化”；ARCHITECTURE §3.6 写作“尚未驻留”。要点是类型已经不透明，换存储时调用方不用改。

K 线：一行 vs 一列

阶段 1 只支持 K 线。向量化层不用 Bar 结构体，而是读 OhlcvPanel：五个字段各一块 n_rows × n_cols 的列主序 Vec<f64>（空 Vec 表示没提供）。 原因是止损引擎分几趟分别读 open、high、low；数组结构体（AoS）每读一个字段都会把整行拉进缓存。

同样 3 根 K 线 × 1 个标的：Bar（AoS，阶段 2）与 OhlcvPanel（SoA，阶段 1）。高亮：止损检查一趟只读 low

Bar 带两个时间戳：ts_event 是 K 线在交易所收盘的时间，ts_init 是它到达引擎的时间。回放必须按 ts_init 排序，因为只有它不会泄露未来。

定点数：Price 与 Quantity

Price { raw: i64, precision: u8 }、Quantity { raw: u64, precision: u8 }。“没有价格”用 Price::UNDEF（raw = i64::MAX）， “算不出来”用 Price::ERROR（raw = i64::MIN），而不是 Option：内核在最内层循环读价格，Option 的判别值是每根 K 线每列一次分支。 代价是对哨兵做算术不会编译报错，所以构造函数是唯一的把关点。

raw 按每个实例的精度缩放

测试里 Price::from_raw(150_500, 3) 是 150.500 JPY，from_raw(6_500_012_345_678, 8) 是 65,000.12345678：raw = 值 × 10precision。模块注释里“raw = 值 × 10PRECISION（9）”描述的是默认刻度，不是每个实例。

derive 的比较只看字段

Eq 与 Ord 是 derive 的：先比 raw 再比 precision。精度不同时它们没有数值意义——1.00 与 1.000 不相等，1.00 还“大于” 5.0。注释说“精度不同的价格做运算前必须先对齐”，目前没有提供对齐的函数。

为什么要准备 i128

PriceRaw 是类型别名。9 位小数下 i64 的上限约 92 亿，价格够用，但链上 18 位小数的数量放不下；高精度变体（16 位小数，i128）只需改别名，不用重写。

撮合枚举的语义跟参考实现走

除了 CashFlowKind，每个撮合枚举的变体和含义都对应 vectorbt。想“改进”某个模式的语义，等于让 tests/fixtures/*.tsv 对不上——那些夹具不能为了让改动通过而重新生成。

解析从右边切

InstrumentId 用 rsplit_once('.')，BarType 用 rsplitn(5, '-')：标的名可以含 . 和 -，交易所名不能含 .（from_parts 显式拒绝）。改成从左边切会让 BTC-USDT 这类标的全部解析错。

定点类型先别拿来算

阶段 1 没有任何地方构造 Price / Quantity，也没有对齐精度的运算。要用它们之前，先补上“按精度对齐”的比较与算术，否则 derive 出的 Ord 会在精度不同时给出错误的大小关系。
